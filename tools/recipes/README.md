# Рецепты — ad-hoc скрипты живых заявок

Всё, что пришлось написать руками вместо готовой команды, оседает здесь, а не в чате.
Два повода держать это в репо:

1. **Переиспользование.** На следующей заявке рецепт гоняется одной командой, а не пишется заново.
2. **Очередь на автоматизацию.** Каждый рецепт — заявка на команду `szcli`: если скрипт
   понадобился дважды, ему место в CLI, а не здесь. Колонка «во что должно вырасти» ниже —
   рабочий список, парный к `docs/dev-backlog.md`.

Правило то же, что и для бэклога (CLAUDE.md): **написал скрипт по ходу заявки — положи сюда
в тот же заход**, с комментарием, какая грабля его породила. Скрипт без объяснения «зачем»
через месяц никто не рискнёт запустить.

## client/ — гоняются на клиенте

Через агента, без SSH: `szcli exec <СЗ> -f tools\recipes\client\<файл>.ps1`

| Скрипт | Что делает | Во что должно вырасти |
|---|---|---|
| `erp-fetch-raw.ps1` | сырой ответ API учётной системы по одной заявке (`sz.fetch`) в файл: захват клиента, вызов, гарантированное освобождение в `finally`. Породил его тот факт, что DTO нельзя строить по описанию API — снятая с живой заявки фикстура сразу показала расхождения (пустые комплектация и переписка, `assembly=null` при готовой сборке). Таймаут 600 с: в 180 с живой вызов не уложился | `szcli sz fetch <СЗ>` — заявка, заказ и состав прямо в `kb/СЗ/<номер>/` (ишью #192) |
| `inventory.ps1` | папка агента, тулы, задачи `szdiag-*`, процессы стресс-тулов, GPU/CPU/диск, Defender+HVCI | `szcli client info <СЗ>` — состояние клиента одной командой перед прогоном |
| `boot-time.ps1` | boot-time/uptime/таймзона глазами клиента — сверка с hub | не нужен после фикса бэклог-п.90 |
| `prep-stress.ps1` | `C:\OCCT` + исключение Defender на `lhmmon`, предупреждение про HVCI | `szcli sensors prep <СЗ>` с парным откатом (бэклог п.38) |
| `make-gpu-schedule.ps1` | GPU-профиль OCCT из эталона: `Gpu3d` → `Vram` → `GpuUnreal` Switch → `PowerSupply`. Донор — `schedule-long.json` или `schedule.json` (что лежит), отсутствие эталона = ошибка, а не пустышка (п.109) | профили в `szcli test run <СЗ> --profile gpu` |
| `make-cpu-schedule.ps1` | CPU-профиль OCCT из эталона: `CpuOcct` (Large) → `CpuOnlyOcct` (Small) → `CpuLinpack`. Конфиги тестов правятся **явно**: донорский `CpuOnlyOcctConfig` приходит `Threads=Fixed/1` + `Mode=Normal` — копия донора грузит одно ядро и рапортует «выстоял» (161346) | профили в `szcli test run <СЗ> --profile cpu` |
| `make-split-schedule.ps1` | расписание-**разделитель ветки** для немого hard-off: фазы по возрастанию потребления `CpuOnlyOcct` → `CpuOcct` (Large) → `PowerSupply`. Момент вырубона = вердикт: лёг на CPU-фазах (~200 Вт) — БЖ снят арифметикой, лёг только на пике CPU+GPU — ветка питания (161498) | `szcli test run <СЗ> --profile split` |
| `sleep-cycle-test.ps1` / `sleep-cycle-stop.ps1` | цикл «сон → RTC-пробуждение» под SYSTEM с логом через AppendAllText: тест дефекта, который **не ловится нагрузкой** (161498 — 65 мин OCCT чисто, а падает в простое). Признак дефекта — 6008 на следующей загрузке, а не «не проснулась». **Перед первым сном** проверяет `Get-LocalUser`/`PasswordLastSet` и `AutoAdminLogon` (161716, 26.08): пароль есть — а автологин после S3, в отличие от загрузки, Windows не применяет — и без `$ConfirmRisk = $true` останавливается, не давая запереть сессию до прихода мастера (бэклог п.224) | `szcli idle-test <СЗ>` — прогон простоя/сна с вердиктом по 6008 |
| `make-combined-schedule.ps1` | **Combined нужной длительности** (`schedule-combined.json`): CPU+RAM+GPU разом — режим максимума транзиентов, которым на 159873 дефект воспроизвёлся за минуты против 5 часов игры. Печатает СОСТАВ подтестов и ругается, если GPU или Memory в доноре выключены | `szcli stress start <СЗ> --profile combined --for 45m` |
| `make-mem-schedule.ps1` | **расписание OCCT только по памяти** (`Memtest`, 95 % ОЗУ, `schedule-mem.json`). Нужен там, где TM5 покрывает лишь часть памяти (161288: 1.3 ГБ × 12 ≈ 15.6 ГБ из 32) и там, где у машины нет человека — у `Memtest` нет окон, в отличие от TM5 | профиль `szcli test run <СЗ> --profile mem` |
| `start-occt-mem.ps1` | **запуск OCCT Memtest с гарантированным отчётом** задачей под SYSTEM. На 162367 прогон 24.08 отработал час и результата не осталось нигде: без ключа `--auto-save-report` CLI отчёт не пишет вообще, а `SaveReportPath` в конфиге — только каталог по умолчанию для GUI. Плюс лицензия вида `license (2).oke`, которую OCCT не видит, и `--auto-close=true`, без которого процесс висит после расписания. Приёмка — по свободной памяти сразу после старта, а не по «задача запущена» | ключи отчёта в `szcli stress start`/`test run`: прогон без сохранённого отчёта не должен быть возможен |
| `secure-boot-state.ps1` | **снимок Secure Boot / TPM / ключей UEFI** одной командой: версия BIOS, режим загрузки, `Confirm-SecureBootUEFI`, `SetupMode`, размеры `PK/KEK/db/dbx`, состояние TPM. На 162367 закрыл спор «перешейте BIOS на старую версию»: Secure Boot включён, ключи штатные, подписанная Windows грузится — значит Violation ловит PXE-загрузчик клиента, а не железо; размер `dbx` показывает, насколько свежий список отзывов приехал с прошивкой | секция `secureboot` в `szcli diag run` |
| `start-sensors.ps1` | `lhmmon` задачей под SYSTEM + приёмка (нули в CPU = драйвер не поднялся) | `szcli sensors start` уже даёт GPU (%, °C, Вт через `nvidia-smi`) — рецепт нужен ради **вольтажей и линий питания**, которых у наблюдателя нет |
| `start-occt.ps1` | клон интерактивной задачи OCCT с подменой расписания | `szcli stress start <СЗ> --schedule <файл>` |
| `check-load.ps1` | хвост CSV: нагрузка реально идёт или это часы простоя | часть `szcli sensors status` |
| `check-voltages.ps1` | какие линии питания на этой машине реально мерятся (+ защита от заглушки-константы) | секция в `szcli sensors report` |
| `idle-check.ps1` | машина реально СТОИТ: аптайм, стресс-процессы, задачи, сон/гибернация, последние 41/6008 | `szcli list` должен различать «простаивает» и «под нагрузкой» |
| `kp41-detail.ps1` | разбор `Kernel-Power 41` по полям: кнопка / BSOD / hard-off + WHEA за период. Окно — 30 дней: на 161346 машину привезли через две недели после дефекта, и 14 дней вернули пустоту (бэклог п.123) | `szcli reboots` должен сверяться с журналом клиента и печатать код BSOD (бэклог п.97, п.121) |
| `power-timeline.ps1` | что машина делала на самом деле: старты/остановы ОС (Kernel-General 12/13), грязные выключения (6008), уход в сон и подъёмы (42/107, Power-Troubleshooter 1 с «проспано N ч»), KP41. На 161346 показал, что «Uptime 11 суток» — это **сон в S3 11 діб 18 год**, а не работа (бэклог п.132) | секция `система` должна печатать `Uptime` с вычетом сна и наработку по SMART (бэклог п.132) |
| `nvme-smart.ps1` | настоящий SMART для NVMe (log page 02h через IOCTL): **Unsafe Shutdowns**, Power Cycles, Power On Hours, Media Errors, Critical Warning словами, износ, Data Units R/W. Штатная секция `storage` эти поля отдаёт **пустыми** — `Get-StorageReliabilityCounter` их на NVMe не знает; **в PE та же дыра ещё шире** (`PowerOnHours`/`StartStopCycles` пустые даже без диагноза «NVMe»), а этот рецепт держится на голом `IOCTL_STORAGE_QUERY_PROPERTY` + `Get-PhysicalDisk`, от модуля Storage не зависит и в PE не проверялся живьём, но по устройству кода должен работать так же (бэклог п.192) | втянуть в пробу `storage` для `BusType=NVMe` (бэклог п.120) |
| `hw-fingerprint.ps1` | **паспорт железа + дифф**: плата, BIOS, CPU, память по слотам (SN, партномер, фактическая частота), накопители с моделью/SN/**слотом PCI bus:dev:fn**, GPU, сеть. Снимок в JSON, при повторе печатает расхождения. Гнать ПЕРВЫМ на новой СЗ: на 161346 шоурум переставил NVMe местами до диагностики, и 8,5 часов прогонов ушли в раскладку, где дефекта не было (бэклог п.136) | снимать автоматом при регистрации СЗ, хранить в SQLite, предупреждать в `list`/`watch` (бэклог п.136) |
| `disk-stress-write.ps1` | нагрузка накопителя **записью + обратным чтением со сверкой SHA каждого блока**, мимо кэша ОС (`WriteThrough`), в свободное место своим файлом (данные клиента не трогаются, файл удаляется даже при обрыве). Дополняет `disk-stress.ps1` (только чтение): `disk 7` = bad block, а он чаще вылезает на записи (бэклог п.133) | шаг `szcli test run` для дисковой версии; сейчас гоняется через `szcli exec --detach` |
| `disk-linear-scan.ps1` | **лінійне читання всього обсягу накопичувача** raw-пристроєм (`\\.\PhysicalDriveN`, блок 4 МБ, повз кеш ФС) зі швидкістю по вікнах 4 ГБ і списком просадок — відтворення сценарію Victoria/HD Tune. На 161972 клієнт заявив «100 % завантаження диска і до 3 МБ/с, потім виліт»: ні `y-cruncher`/OCCT (накопичувач не чіпають узагалі), ні `disk-stress.ps1` (файли, випадковий доступ) цей профіль не перевіряють | секція `storage` у `szcli test run` — лінійний скан із графіком швидкості по зонах |
| `disk-zone-map.ps1` | **карта швидкості по всьому обсягу точками** (`map`: N точок × 32 МБ — весь диск за хвилини) і **прицільний сплошняк по зоні** (`zone`: межі в ГБ, крок звіту). Потрібен, бо суцільне читання по деградованій зоні не закінчується: на 161972 просадка до 9,6 МБ/с означала б добу на повний прохід 1863 ГБ | те саме, що й `disk-linear-scan.ps1` — `szcli disk scan <СЗ> [--map\|--zone A-B]` (бэклог п.200) |
| `disk-fill.ps1` | **заповнення накопичувача даними** (файли по 8 ГБ у власній папці, випадковий вміст, звіт швидкості по кожному) — підготовка до повторного лінійного читання **після чистої установки з швидким форматом**. Грабля 161972 (25.08): швидкий формат = TRIM на весь обсяг, порожні LBA контролер віддає нулями повз NAND, і скан дефектної зони пролітає на 5600 МБ/с просто тому, що читати нічого. Заодно міряє запис: вихід за SLC-кеш видно як обвал | секція запису в `szcli disk snapshot/scan` (бэклог п.213) |
| `disk-number-history.ps1` | **кто был `HarddiskN`/`RaidPortN` в момент архивной ошибки**: история из `Partition/Diagnostic` 1006 (номер диска, `Adapter` = N в `\Device\RaidPortN`, `Bus` = слот, модель, SN) + список подключавшихся флешек + дисковые ошибки за окно. На 161346 вскрыл, что диски **поменяли местами 29.07**, и привязка ошибок была зеркальной (бэклог п.133) | резолв `\Device\HarddiskN` на момент события в секции `storage`/`reboots` (бэклог п.133) |
| `kp41-where.ps1` | **где и когда машина упала**: `Kernel-Power 41` пишется при загрузке и описывает ПРЕДЫДУЩИЙ сеанс, поэтому дата события ≠ дата отказа. Сводит каждое событие к «когда подняли → какой сеанс упал → сколько прожил → в чьей сети шёл». На 161346 показал, что 11 из 25 вырубонов случились не у клиента, а на точке сборки (бэклог п.161) | `szcli reboots` обязан раскладывать вырубоны по месту, иначе чужие события уезжают клиенту как его (бэклог п.161) |
| `net-signatures.ps1` | **чья это была сеть**: MAC шлюза каждого сетевого профиля (`NetworkList\Signatures`) + журнал подключений. Имя профиля не значит ничего — оно приезжает внутри образа; MAC шлюза сверяют с роутером конкретной точки. На 161346 доказал, что диски переставляли на точке сборки, а не в боксе (бэклог п.161) | `szcli where <СЗ>` — таймлайн «в чьей сети стояла машина», с известными шлюзами в конфиге hub (бэклог п.161) |
| `net-window.ps1` | сеть + питание + `Partition/Diagnostic` за окно дат одним срезом: где стояла машина, когда стартовала и падала, в каких слотах были накопители. Нужен, когда спор идёт про конкретный день, а полный журнал за месяц не влезает в вывод | часть будущей `szcli where` (бэклог п.161) |
| `net-watch.ps1` | **вахта за линком**: посекундно состояние, скорость против опорной, счётчики ошибок/дискардов, пинг шлюза **своего** интерфейса; лог с flush переживает и отвал, и вырубон. Ловит не только обрыв, но и тихую переторговку `2.5G → 100 Mbps` — связь есть, PXE-образ по ней уже не едет. Шлюз берётся строго у сторожимого адаптера: «первый попавшийся» дал `26.0.0.1` от Radmin VPN и ложное «ПИНГ ПРОПАЛ» на живой сети (СЗ 162367, бэклог п.203). Гнать `--detach` и **обязательно с трафиком** — на простое отвал не воспроизводится | `szcli net watch <СЗ>` с записью событий в журнал СЗ (бэклог п.203) |
| `net-load.ps1` | **нагрузка на сеть**: клиент по кругу тянет крупный файл с шары бокса, скорость по окнам, просадки и обрывы SMB-сессии в лог. Пара к `net-watch.ps1` — вахта без трафика бесполезна, отвал на простое не воспроизводится. Читает в никуда (диск клиента не трогается), шару размонтирует даже при падении | `szcli net load <СЗ>` / профиль сетевой нагрузки в `test run` (бэклог п.203) |
| `net-adapter-power.ps1` | **энергосбережение и режимы адаптера** (только чтение): Green Ethernet, Gigabit Lite, Power Saving Mode, EEE, `PnPCapabilities`, Speed & Duplex, Wake-on-*. На 162367 нашёл включённые Green Ethernet + Gigabit Lite + Power Saving Mode — фирменные режимы Realtek, режущие передатчик по длине кабеля, главный подозреваемый по «отваливается сеть». Этих параметров нет ни в одной секции `diag.md` | секция `net` в RunDiag (бэклог п.203) |
| `net-power-off.ps1` | **гасит Green Ethernet / Gigabit Lite с бэкапом и откатом** (`$Restore = $true`). Значение пишется СЫРЫМ в реестр через пару `ValidDisplayValues`/`ValidRegistryValues` — `-DisplayValue 'Disabled'` падает на украинской и русской винде. Бэкап пишется ДО первой правки: смена параметра ресетит адаптер и рвёт exec-канал на полуслове (162367 — агента потом поднимали по SSH, бэклог п.202) | `szcli net tune <СЗ>` с парным откатом в `close`, как у `freeze`/`unfreeze` (бэклог п.203) |
| `net-link-history.ps1` | **отваливалась ли сеть ДО сервиса**: разрывы линка (NDIS), ошибки DHCP, профили сети и события драйвера NIC за N дней, эпизоды «упал → поднялся» с длительностью. Главное — **различает «канал выключен» и «событий не было»**: `NDIS/Operational` и `Dhcp-Client/Operational` на клиентской винде выключены по умолчанию, и пустой журнал читается как «сетевуха здорова» — ложный вывод, из-за которого заявка приезжает снова (СЗ 162367, бэклог п.203) | `szcli net history <СЗ>` (бэклог п.203) |
| `os-provenance.ps1` | **образ или чистая установка**: `CloneTag` (метка снятия образа), `GeneralizationState` (sysprep), даты создания тома и системных папок, начало `setupapi.dev.log`, призраки чужого железа, `Windows.old`, статус активации. На 161346 подтвердил раскатку образа от 01.04.2024 и опроверг версию клиента про чужие драйверы (бэклог п.162) | секция `os` в RunDiag — снимок происхождения системы (бэклог п.162) |
| `crash-snapshot.ps1` | снимок сразу после отказа, пока машина живая: раскладка слотов, SMART, KP41 с bugcheck, ошибки накопителей, свежие минидампы. Машина после отвала живёт минутами — ходить за этим по очереди значит потерять половину | шаг после срабатывания монитора вырубона |
| `slot-watch.ps1` | вахта за составом NVMe раз в 5 с + `stornvme`/`disk`/WHEA. Ловит отвал **несистемного** диска: система при этом выживет и промолчит. | `slot-map.ps1` | быстрая карта **накопитель → шина PCI (слот)** + серийник, прошивка, буква тома и имя в журнале (`\Device\HarddiskN\DRN`), плюс последние `Partition/Diagnostic` 1006. | `wu-driver-history.ps1` | что Windows Update поставил за окно и когда менялись драйверы железа. ## Грабли, зашитые в рецепты

Это не стиль, а причины — при правке не убирать:

- **`szcli exec` не передаёт аргументы, а `param()` в рецепте прямо ломает запуск.** Агент
  клеит свою шапку (кодировка + `$ProgressPreference`) **перед** телом скрипта, а `param(...)`
  в PowerShell обязан быть первым выражением — на 260306 это дало
  `param : The term 'param' is not recognized`, причём скрипт не упал, а молча отработал мимо
  аргументов и выдал неверный результат. Параметры выносить переменными в шапку файла
  (`$Sz`, `$Schedule`), правятся перед запуском. Настоящий фикс — бэклог п.102.
- **Рецепт, который печатает «готово», обязан проверить результат.** `make-gpu-schedule.ps1`
  рапортовал «записан: …\schedule-gpu.json», а файла на клиенте не было — выяснилось
  заявкой позже. Пишешь файл — `Test-Path` после записи; нет исходных данных — `throw`,
  а не пустой результат (п.109).
- **UTF-8 с BOM обязателен.** Без BOM PowerShell 5.1 ломает кириллицу и файл падает
  с `The string is missing the terminator` — это не про кодировку вывода, а про парсинг.
  Касается и скриптов в `tools/`: 2026-08-07 без BOM оказались `doctor.ps1`,
  `occt-schedule.ps1` и два рецепта — `doctor.ps1` не запускался вообще (бэклог п.112).
- **Расписание OCCT из одного периода нужно собирать через `@(...)`.** `$sched.Periods = foreach (…)`
  при единственном элементе даёт скаляр, `ConvertTo-Json` пишет `"Periods": {…}` вместо `[{…}]`,
  и OCCT отвечает `Could not load the schedule file - file does not exists` — **про существующий
  файл** (161346: догон Linpack «отработал» за минуту с нулевой нагрузкой). После записи проверять
  регуляркой, что `Periods` сериализован массивом (бэклог п.128).
- **Перед отправкой скрипта проверять синтаксис** локально:
  `[System.Management.Automation.PSParser]::Tokenize((Get-Content -Raw <файл>), [ref]$e)` —
  дешевле, чем ловить парс-ошибку в выводе агента.
- **CSV сенсоров читать только `ConvertFrom-Csv`/`Import-Csv`.** Ручной `split ','` по шапке
  уезжает на одну колонку (BOM + `timestamp` склеены с первым датчиком), и GPU clock 2210
  читается как «температура 1058».
- **Тяжёлое запускать только задачами** (`schtasks`), не `Start-Process` из exec-сессии:
  под нагрузкой сессия глохнет и уносит дочерний процесс (бэклог п.53).
- **OCCT — в своём окне** (`start /min`) и с интерактивным токеном: при перенаправлённом
  stdout он тихо умирает (п.40), а 3D-тест не рендерится в сессии 0.
- **Приёмка прогона — по сенсорам, а не по «тест запущен».** 3D-сцена поднимается не мгновенно:
  на 75-й секунде GPU может стоять на нуле, а на 4-й минуте уже 100 % / 192 Вт.
- **`[datetime]::TryParse($s, [ref]$t)` в PS 5.1 падает** «Cannot find an overload for TryParse
  and the argument count 2», если `$t` не типизирована, а `Parse` на клиентской локали (uk-UA)
  жуёт `2026-08-11 13:03:34` по-своему. Разбирая время из чужих логов — только
  `[datetime]::ParseExact(..., 'yyyy-MM-dd HH:mm:ss', [Globalization.CultureInfo]::InvariantCulture)`
  в `try/catch` (`game-session-log.ps1`).
- **Бэкап состояния для парного отката — пишется РОВНО ОДИН РАЗ.** На 161190 (бэклог п.171)
  `gpu-p0-fix-ledkeeper.ps1` сохранял исходное состояние служб при КАЖДОМ запуске: первый
  прогон честно записал `Mystic_Light_Service = Auto/Running`, но второй (доработка лечения)
  перезаписал точку возврата уже изменённым состоянием (`Disabled/Stopped`) — `$Restore`
  потом «вернул» подсветку в уже поломанное состояние, искренне считая его исходным. Если
  файл состояния уже есть — не трогать его и сказать об этом в выводе; новые изменения
  писать отдельным слоем. Тот же принцип, что у `RevertState` агента (прогрессивная запись
  переживает краш) — только там он соблюдён с самого начала. Заодно: в откате печатать, что
  именно возвращается, **до** применения — иначе поломанное «исходное» не видно, пока не
  стало поздно.
- **Запись на удалённую шару — проверять по `FullName`, а не по «ошибок не было».** На 161946
  (бэклог п.216) `net use \\192.168.94.123\Share ...` упал `System error 67` (SMB-редиректор
  не поднят в PE), но дальше `Test-Path`/`Copy-Item`/`Get-ChildItem` отработали **без единой
  ошибки** — PowerShell молча подменил недоступный UNC локальным относительным путём на
  RAM-диске (`X:\192.168.94.123\Share\...`), и 13 МБ уехали в никуда с виду успешно. Проверка:
  ```powershell
  if ((Get-Item $dst).FullName -notlike '\\*') { "SMB недоступен: $dst — путь не UNC"; return }
  ```
  Если писать по UNC вообще не получается (как в PE) — канал доставки **клиент → хост** уже
  формализован без SMB: `pe-file-out-base64.ps1` (zip + base64-чанки через stdout `exec`,
  sha256-сверка на хосте) — им и пользоваться, а не изобретать SMB-запись заново.
- **`Get-WinEvent -Path`/`FileInfo.LastWriteTime` в PE конвертируют время в таймзону PE, не
  клиента.** На 161498 (бэклог п.227) KP41 из офлайн-журнала показался как 05:13 вместо
  реальных 16:13 у клиента — PE стартует в Pacific, клиент живёт в Киеве, сдвиг 11 ч. Печатать
  UTC (`$e.TimeCreated.ToUniversalTime()` — симметричный откат конвертации PE корректно
  восстанавливает истинный UTC-момент независимо от зоны PE; для файловых времён —
  `.LastWriteTimeUtc`, `[datetime]::FromFileTimeUtc(...)` вместо `FromFileTime`), с пометкой
  «UTC» в заголовке вывода. Дельты (сколько прожил сеанс и т.п.) от сдвига не зависят и без
  этой правки — портится только АБСОЛЮТНОЕ печатаемое время.
- **Ограничения WinPE — один список, а не грабли по кругу в каждом `pe-*.ps1`.** Нет модуля
  PnpDevice (`Get-PnpDevice` → `CommandNotFoundException`, замена — `Get-CimInstance
  Win32_PnPEntity`), `Get-StorageReliabilityCounter` отдаёт только `Temperature`/`Wear`
  (`PowerOnHours`/`StartStopCycles` пустые — для NVMe заменяет `nvme-smart.ps1`, он держится
  на голом IOCTL и от Storage-модуля не зависит), тома часто без буквы. Полный список — в
  шапке `pe-offline-triage.ps1` (бэклог п.192).
- **Привязку события к сессии не делать фиксированным окном.** Первая версия
  `game-session-log.ps1` считала вырубон «игровым», если он в 90 минутах от старта игры — и
  7,7-часовая сессия ушла в графу «вне игры», занизив связь. Интервал сессии считать по
  фактическим границам (`removed` / следующий старт / разумный потолок), а не по константе
  (бэклог п.138).
- **Скрипты для `szcli exec -f` писать инструментом Write, не heredoc'ом bash.** `cat > f <<'EOF'`
  в Git Bash **схлопывает `\` в `\`**, и регулярка вида `'(\Device\Harddisk\d+)'` приезжает
  на клиент сломанной: `Unrecognized escape sequence \H`. Отладка при этом уходит в PowerShell,
  хотя ломается на записи файла. Для устройств из событий вообще не парсить текст сообщения —
  брать `$_.Properties[0].Value` (бэклог п.143).
- **Правку тяжело экранируемых строк (`\.\PhysicalDrive` и подобные) — проверять по байтам.**
  На 160705 (бэклог п.178) слеш терялся молча в цепочке `bash → heredoc → python → PowerShell`,
  скрипт синтаксически оставался корректным и падал уже на клиенте (`CreateFile failed win32=2`,
  выглядит как «диска нет», хотя диск на месте); две попытки починить через тот же heredoc
  молча не применились. Такие строки в C#/PowerShell собирать из констант
  (`@"\\.\PhysicalDrive"` в C# — verbatim-строка, слеши буквальные и не нуждаются в
  экранировании — как в `nvme-smart.ps1`), а после правки сверять код символов
  (`[byte[]][char[]]$s` в PowerShell, `chr(92)`/`0x5c` — по обе стороны), а не глазами.
