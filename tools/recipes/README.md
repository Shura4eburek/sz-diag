# Рецепты — ad-hoc скрипты живых заявок

Всё, что пришлось написать руками вместо готовой команды, оседает здесь, а не в чате.
Два повода держать это в репо:

1. **Переиспользование.** На следующей заявке рецепт гоняется одной командой, а не пишется заново.
2. **Очередь на автоматизацию.** Каждый рецепт — заявка на команду `szcli`: если скрипт
   понадобился дважды, ему место в CLI, а не здесь. Колонка «во что должно вырасти» ниже —
   рабочий список, парный к `docs/dev-backlog.md`.

Правило то же, что и для бэклога (CLAUDE.md): **написал скрипт по ходу заявки — положи сюда
в тот же заход**, с комментарием, какая грабля его породила. Скрипт без объяснения «зачем»
через месяц никто не рискнёт запустить.

## client/ — гоняются на клиенте

Через агента, без SSH: `szcli exec <СЗ> -f tools\recipes\client\<файл>.ps1`

| Скрипт | Что делает | Во что должно вырасти |
|---|---|---|
| `inventory.ps1` | папка агента, тулы, задачи `szdiag-*`, процессы стресс-тулов, GPU/CPU/диск, Defender+HVCI | `szcli client info <СЗ>` — состояние клиента одной командой перед прогоном |
| `boot-time.ps1` | boot-time/uptime/таймзона глазами клиента — сверка с hub | не нужен после фикса бэклог-п.90 |
| `prep-stress.ps1` | `C:\OCCT` + исключение Defender на `lhmmon`, предупреждение про HVCI | `szcli sensors prep <СЗ>` с парным откатом (бэклог п.38) |
| `make-gpu-schedule.ps1` | GPU-профиль OCCT из эталона: `Gpu3d` → `Vram` → `GpuUnreal` Switch → `PowerSupply`. Донор — `schedule-long.json` или `schedule.json` (что лежит), отсутствие эталона = ошибка, а не пустышка (п.109) | профили в `szcli test run <СЗ> --profile gpu` |
| `make-cpu-schedule.ps1` | CPU-профиль OCCT из эталона: `CpuOcct` (Large) → `CpuOnlyOcct` (Small) → `CpuLinpack`. Конфиги тестов правятся **явно**: донорский `CpuOnlyOcctConfig` приходит `Threads=Fixed/1` + `Mode=Normal` — копия донора грузит одно ядро и рапортует «выстоял» (161346) | профили в `szcli test run <СЗ> --profile cpu` |
| `make-combined-schedule.ps1` | **Combined нужной длительности** (`schedule-combined.json`): CPU+RAM+GPU разом — режим максимума транзиентов, которым на 159873 дефект воспроизвёлся за минуты против 5 часов игры. Печатает СОСТАВ подтестов и ругается, если GPU или Memory в доноре выключены | `szcli stress start <СЗ> --profile combined --for 45m` |
| `make-mem-schedule.ps1` | **расписание OCCT только по памяти** (`Memtest`, 95 % ОЗУ, `schedule-mem.json`). Нужен там, где TM5 покрывает лишь часть памяти (161288: 1.3 ГБ × 12 ≈ 15.6 ГБ из 32) и там, где у машины нет человека — у `Memtest` нет окон, в отличие от TM5 | профиль `szcli test run <СЗ> --profile mem` |
| `start-sensors.ps1` | `lhmmon` задачей под SYSTEM + приёмка (нули в CPU = драйвер не поднялся) | `szcli sensors start` уже даёт GPU (%, °C, Вт через `nvidia-smi`) — рецепт нужен ради **вольтажей и линий питания**, которых у наблюдателя нет |
| `start-occt.ps1` | клон интерактивной задачи OCCT с подменой расписания | `szcli stress start <СЗ> --schedule <файл>` |
| `check-load.ps1` | хвост CSV: нагрузка реально идёт или это часы простоя | часть `szcli sensors status` |
| `check-voltages.ps1` | какие линии питания на этой машине реально мерятся (+ защита от заглушки-константы) | секция в `szcli sensors report` |
| `idle-check.ps1` | машина реально СТОИТ: аптайм, стресс-процессы, задачи, сон/гибернация, последние 41/6008 | `szcli list` должен различать «простаивает» и «под нагрузкой» |
| `kp41-detail.ps1` | разбор `Kernel-Power 41` по полям: кнопка / BSOD / hard-off + WHEA за период. Окно — 30 дней: на 161346 машину привезли через две недели после дефекта, и 14 дней вернули пустоту (бэклог п.123) | `szcli reboots` должен сверяться с журналом клиента и печатать код BSOD (бэклог п.97, п.121) |
| `power-timeline.ps1` | что машина делала на самом деле: старты/остановы ОС (Kernel-General 12/13), грязные выключения (6008), уход в сон и подъёмы (42/107, Power-Troubleshooter 1 с «проспано N ч»), KP41. На 161346 показал, что «Uptime 11 суток» — это **сон в S3 11 діб 18 год**, а не работа (бэклог п.132) | секция `система` должна печатать `Uptime` с вычетом сна и наработку по SMART (бэклог п.132) |
| `nvme-smart.ps1` | настоящий SMART для NVMe (log page 02h через IOCTL): **Unsafe Shutdowns**, Power Cycles, Power On Hours, Media Errors, Critical Warning словами, износ, Data Units R/W. Штатная секция `storage` эти поля отдаёт **пустыми** — `Get-StorageReliabilityCounter` их на NVMe не знает | втянуть в пробу `storage` для `BusType=NVMe` (бэклог п.120) |
| `hw-fingerprint.ps1` | **паспорт железа + дифф**: плата, BIOS, CPU, память по слотам (SN, партномер, фактическая частота), накопители с моделью/SN/**слотом PCI bus:dev:fn**, GPU, сеть. Снимок в JSON, при повторе печатает расхождения. Гнать ПЕРВЫМ на новой СЗ: на 161346 шоурум переставил NVMe местами до диагностики, и 8,5 часов прогонов ушли в раскладку, где дефекта не было (бэклог п.136) | снимать автоматом при регистрации СЗ, хранить в SQLite, предупреждать в `list`/`watch` (бэклог п.136) |
| `disk-stress-write.ps1` | нагрузка накопителя **записью + обратным чтением со сверкой SHA каждого блока**, мимо кэша ОС (`WriteThrough`), в свободное место своим файлом (данные клиента не трогаются, файл удаляется даже при обрыве). Дополняет `disk-stress.ps1` (только чтение): `disk 7` = bad block, а он чаще вылезает на записи (бэклог п.133) | шаг `szcli test run` для дисковой версии; сейчас гоняется через `szcli exec --detach` |
| `disk-number-history.ps1` | **кто был `HarddiskN`/`RaidPortN` в момент архивной ошибки**: история из `Partition/Diagnostic` 1006 (номер диска, `Adapter` = N в `\Device\RaidPortN`, `Bus` = слот, модель, SN) + список подключавшихся флешек + дисковые ошибки за окно. На 161346 вскрыл, что диски **поменяли местами 29.07**, и привязка ошибок была зеркальной (бэклог п.133) | резолв `\Device\HarddiskN` на момент события в секции `storage`/`reboots` (бэклог п.133) |
| `kp41-where.ps1` | **где и когда машина упала**: `Kernel-Power 41` пишется при загрузке и описывает ПРЕДЫДУЩИЙ сеанс, поэтому дата события ≠ дата отказа. Сводит каждое событие к «когда подняли → какой сеанс упал → сколько прожил → в чьей сети шёл». На 161346 показал, что 11 из 25 вырубонов случились не у клиента, а на точке сборки (бэклог п.161) | `szcli reboots` обязан раскладывать вырубоны по месту, иначе чужие события уезжают клиенту как его (бэклог п.161) |
| `net-signatures.ps1` | **чья это была сеть**: MAC шлюза каждого сетевого профиля (`NetworkList\Signatures`) + журнал подключений. Имя профиля не значит ничего — оно приезжает внутри образа; MAC шлюза сверяют с роутером конкретной точки. На 161346 доказал, что диски переставляли на точке сборки, а не в боксе (бэклог п.161) | `szcli where <СЗ>` — таймлайн «в чьей сети стояла машина», с известными шлюзами в конфиге hub (бэклог п.161) |
| `net-window.ps1` | сеть + питание + `Partition/Diagnostic` за окно дат одним срезом: где стояла машина, когда стартовала и падала, в каких слотах были накопители. Нужен, когда спор идёт про конкретный день, а полный журнал за месяц не влезает в вывод | часть будущей `szcli where` (бэклог п.161) |
| `os-provenance.ps1` | **образ или чистая установка**: `CloneTag` (метка снятия образа), `GeneralizationState` (sysprep), даты создания тома и системных папок, начало `setupapi.dev.log`, призраки чужого железа, `Windows.old`, статус активации. На 161346 подтвердил раскатку образа от 01.04.2024 и опроверг версию клиента про чужие драйверы (бэклог п.162) | секция `os` в RunDiag — снимок происхождения системы (бэклог п.162) |
| `crash-snapshot.ps1` | снимок сразу после отказа, пока машина живая: раскладка слотов, SMART, KP41 с bugcheck, ошибки накопителей, свежие минидампы. Машина после отвала живёт минутами — ходить за этим по очереди значит потерять половину | шаг после срабатывания монитора вырубона |
| `slot-watch.ps1` | вахта за составом NVMe раз в 5 с + `stornvme`/`disk`/WHEA. Ловит отвал **несистемного** диска: система при этом выживет и промолчит. На 161346 поймала 6 × `disk 7` на тестовом диске в чипсетном слоте — то, что перевело подозрение с накопителя на плату | наблюдатель в `szcli sensors`/`test run` для дисковых версий |
| `slot-map.ps1` | быстрая карта **накопитель → шина PCI (слот)** + серийник, прошивка, буква тома и имя в журнале (`\Device\HarddiskN\DRN`), плюс последние `Partition/Diagnostic` 1006. Лёгкая замена `pcie-topology.ps1`, который **не влезает в 120 с** `exec` (бэклог п.176). Нужна перед каждым прогоном: без неё тест в слоте интерпретируется вслепую. ⚠️ `bus` плывёт (на 161346 сдвинулся на 1 между стартами за 5 минут) — привязка по `adapter`+серийнику | проба `slots` в `diag run`; сейчас через `szcli exec -f` |
| `wu-driver-history.ps1` | что Windows Update поставил за окно и когда менялись драйверы железа. Нужен, когда машина полежала: если после приёмки прилетел драйвер накопителя/чипсета/видео, то тесты идут уже не на той системе, которую сдал клиент | отдельная секция `diag`, чтобы «дефект не воспроизводится» не путать с «его починил апдейт» |
| `nvme-errlog.ps1` | NVMe Error Information Log (page 01h) со Status Code Type/Code словами + карта `Harddisk N → модель/SN → SCSIPort` для привязки `\Device\RaidPortN` из журнала. **Карта строится на «сейчас» — для архивных событий она врёт, брать `disk-number-history.ps1`** (бэклог п.133) | карта — в пробу `storage` (бэклог п.122); сам error log контроллеры Kingston NV3 отдали пустым при `ErrorLogEntries=20` в SMART — перепроверить на другом вендоре |
| `game-session-log.ps1` | **история игровых сессий из логов лаунчеров + привязка к вырубонам**: `Game process added/removed` из Steam-лога (имена игр из `appmanifest_*.acf`), события 41/1074/6008, таблица «запуск → итог → через сколько» и итог «N из M сессий закончились вырубоном». Ключ: `removed` пишется только при штатном выходе, его отсутствие = hard-off прямо в игре. На 160705 за минуту дал то, чего не дали четыре синтетических прогона: 37 из 97 сессий закончились вырубоном (медиана 11,7 мин), но 37 из 74 вырубонов вне игр — версия «падает только в CS2» отброшена (бэклог п.138) | секция `games` в `szcli diag` с автосверкой по `reboots` (бэклог п.138) |
| `apply-ab-profile.ps1` | применить профиль **MSI Afterburner клиента** (разгон/PowerLimit/ручной вентилятор), чтобы прогон шёл в режиме клиента, а не «как приехало». Штатный CLI `-Profile1` возвращает успех и **не применяет ничего** — работает только через ключи автоприменения в конфиге + перезапуск AB. Конфиг клиента бэкапится, `$Restore = $true` возвращает как было. ⚠️ вентилятор слетает в авто при запуске игры, а разгон и PowerLimit — нет (160705) | ключ `szcli test run --profile client` + парный откат |
| `start-game-cs2.ps1` | **CS2 как нагрузочный прогон**: бой с ботами, дезматч с респавном, `fps_max 0`, интерактивная задача. `+map` без `+game_type/+game_mode` карту не поднимает (игра встаёт в меню и даёт 30 % GPU — легко принять за прогон), `engine_no_focus_sleep 0` не даёт душить рендер без человека у машины. На 160705 убил карту за **2 мин 14 с** там, где OCCT молчал 96 минут | `szcli game start <СЗ> cs2` вместе с сенсорами (бэклог п.137) |
| `game-load-check.ps1` | приёмка игрового прогона по ряду `lhmmon`: посекундный хвост + сводка мин/сред/макс, доля замеров с GPU ≥ 60 % и предупреждение «нагрузки нет — проверь, не в меню ли игра». Колонки ищет регуляркой (в CSV они с суффиксом единиц) | часть `szcli sensors report` / приёмки `game start` |
| `ab-profile-history.ps1` | кто и когда трогал настройки Afterburner: время правок профилей, значения (CoreClk/PowerLimit/FanSpeed), установка, запуски по Prefetch, автозапуск, ключи автоприменения. «Кто» система не пишет (аудит файлов выключен) — только косвенно. На 160705 показал, что правка профиля 04.08 16:01 — это **сервис переустанавливал драйвер**, а не клиент | секция в `diag` для заявок, где спорят о разгоне |
| `whea-storage-detail.ps1` | полные тела событий WHEA + дисковых ошибок с резолвом `Harddisk N` в модель; обход упавшей секции `whea` (бэклог п.101) | чинить саму секцию `whea`, а карту дисков — в `storage` (п.101, п.122) |
| `cleanup-stress.ps1` | снятие задач, процессов, **драйвера `R0lhmmon`**, исключения Defender, `C:\OCCT` | закрыто: `szcli client cleanup` + уборка в `Revert` (бэклог п.88/56/99) |
| `check-occt-schedule.ps1` | валидирует `TestType` в расписании OCCT и предупреждает про `CpuLinpack` с дефолтными 2048 МБ | шаг `szcli stress start` (бэклог п.96) |
| `set-occt-schedule.ps1` | подменяет `schedule.json`, который жёстко зашит в шаге `occt` тест-сьюта, на нужное расписание (с сохранением `.orig`) и печатает фактическую длительность | ключ `szcli test run --schedule/--profile` (бэклог п.124) |
| `post-run-check.ps1` | что случилось за прогон: живы ли процессы теста, аварии приложений, KP41/6008, WHEA/disk/stornvme/nvlddmkm, троттлинг, новые минидампы | приёмка в `szcli test run` по завершении (бэклог п.124) |
| `where-tools.ps1` | **где на этой машине реально лежат тулы** + срок лицензии OCCT. Если агент запущен из облачной папки (OneDrive), `push` уводит раздачу в `C:\ProgramData\szdiag\tools`, а тест-раннер и все рецепты ищут `tools\` рядом с агентом — промах выглядит как «процесс НЕ ЗАПУСТИЛСЯ» (161716). Заодно парсит дату из `.oke` и ловит имя вида `license (2).oke`, которое OCCT не видит вообще | единый резолв `ToolsDirectory` для раннера и рецептов + проверка лицензии в `szcli kb doctor` (бэклог п.151, п.152) |
| `task-why.ps1` | **почему задача запустилась, а процесса нет**: `LastTaskResult` с расшифровкой, принципал, действие, журнал планировщика. `0x0` без процесса = exe вышел сам (у OCCT — протухшая лицензия), `0x1` без лога = `cmd /c "exe" args > log` съел кавычки первого токена (161716) | внятная диагностика запуска в `szcli stress start` |
| `start-prime95.ps1` | **prime95 torture Small FFT (4K–32K) — максимальный тепловой режим CPU**, ответ на вопрос «есть перегрев или нет». Задача под SYSTEM (GUI-процесс из сессии агента умирает вместе с exec'ом), `prime.txt` со `StressTester=1` — иначе первый старт молча висит в диалоге. Приёмка по реальной загрузке CPU, а не по факту «задача создана». На 160587 дал вердикт за 48 мин: Tctl 76 °C при лимите 95, частота 4550–4650 без просадок | шаг `prime95` в `testsuite.json` + `szcli stress start <СЗ> --tool prime95` |
| `sensors-peek.ps1` | **максимум за весь прогон** по температурам/мощности/частотам/оборотам, парный к `check-load.ps1` (тот показывает хвост в 20 замеров и легко попадает в паузу между FFT-размерами). Читает оба источника — CSV `szcli sensors` и lhmmon, разделитель определяет по шапке | часть `szcli sensors report`: пиковые значения в шапке отчёта |
| `post-cpu-swap-check.ps1` | **срез после замены процессора**: CPU/BIOS/uptime, частота памяти (`Speed` vs `Configured` — ловит поднятый профиль), вся история WHEA с группировкой по ApicId и датами первого/последнего события, Kernel-Power 41, минидампы. Гнать сразу после свопа: на 160587 показал, что вместе с процессором подняли память 4800 → 5600, а это ломает главный аргумент рекламации «разгона нет» | `szcli diag run <СЗ> whea` должен сам группировать по ApicId и отделять историю до/после замены |
| `start-ycruncher.ps1` | **y-cruncher stress (VT3/N63/FFTv4) — бесплатный ловец нестабильности IMC**, замена OCCT когда лицензия протухла. Давит контроллер памяти сверкой результата вычислений, а не паттернами в ячейках, поэтому берёт там, где TM5 проходит чисто — то есть ровно класс «7500F + DDR5-6000» (159873, 160176, 161716). Приёмка по дочернему процессу из `Binaries\` (`y-cruncher.exe` — лаунчер, своего процесса не держит) | шаг `ycruncher` в `testsuite.json` + `szcli stress start <СЗ> --tool ycruncher` |
| `wipe-tools.ps1` | **снести привезённое `szcli push`**: `tools\{prime95,lhmmon,ycruncher,occt,tm5,furmark,3dmark}` в обоих местах (рядом с агентом и в `ProgramData`) + рабочая `C:\OCCT`, с подсчётом освобождённого. `client cleanup` этого не делает и даже не показывает — на 160306 после «уборки» на клиенте оставалось 100+ МБ наших бинарей (бэклог п.158). Гнать перед `szcli close` | `szcli push` ведёт манифест доставленного, `client cleanup` сносит ровно его, `close` не даёт закрыть СЗ с остатками |

## Грабли, зашитые в рецепты

Это не стиль, а причины — при правке не убирать:

- **`szcli exec` не передаёт аргументы, а `param()` в рецепте прямо ломает запуск.** Агент
  клеит свою шапку (кодировка + `$ProgressPreference`) **перед** телом скрипта, а `param(...)`
  в PowerShell обязан быть первым выражением — на 260306 это дало
  `param : The term 'param' is not recognized`, причём скрипт не упал, а молча отработал мимо
  аргументов и выдал неверный результат. Параметры выносить переменными в шапку файла
  (`$Sz`, `$Schedule`), правятся перед запуском. Настоящий фикс — бэклог п.102.
- **Рецепт, который печатает «готово», обязан проверить результат.** `make-gpu-schedule.ps1`
  рапортовал «записан: …\schedule-gpu.json», а файла на клиенте не было — выяснилось
  заявкой позже. Пишешь файл — `Test-Path` после записи; нет исходных данных — `throw`,
  а не пустой результат (п.109).
- **UTF-8 с BOM обязателен.** Без BOM PowerShell 5.1 ломает кириллицу и файл падает
  с `The string is missing the terminator` — это не про кодировку вывода, а про парсинг.
  Касается и скриптов в `tools/`: 2026-08-07 без BOM оказались `doctor.ps1`,
  `occt-schedule.ps1` и два рецепта — `doctor.ps1` не запускался вообще (бэклог п.112).
- **Расписание OCCT из одного периода нужно собирать через `@(...)`.** `$sched.Periods = foreach (…)`
  при единственном элементе даёт скаляр, `ConvertTo-Json` пишет `"Periods": {…}` вместо `[{…}]`,
  и OCCT отвечает `Could not load the schedule file - file does not exists` — **про существующий
  файл** (161346: догон Linpack «отработал» за минуту с нулевой нагрузкой). После записи проверять
  регуляркой, что `Periods` сериализован массивом (бэклог п.128).
- **Перед отправкой скрипта проверять синтаксис** локально:
  `[System.Management.Automation.PSParser]::Tokenize((Get-Content -Raw <файл>), [ref]$e)` —
  дешевле, чем ловить парс-ошибку в выводе агента.
- **CSV сенсоров читать только `ConvertFrom-Csv`/`Import-Csv`.** Ручной `split ','` по шапке
  уезжает на одну колонку (BOM + `timestamp` склеены с первым датчиком), и GPU clock 2210
  читается как «температура 1058».
- **Тяжёлое запускать только задачами** (`schtasks`), не `Start-Process` из exec-сессии:
  под нагрузкой сессия глохнет и уносит дочерний процесс (бэклог п.53).
- **OCCT — в своём окне** (`start /min`) и с интерактивным токеном: при перенаправлённом
  stdout он тихо умирает (п.40), а 3D-тест не рендерится в сессии 0.
- **Приёмка прогона — по сенсорам, а не по «тест запущен».** 3D-сцена поднимается не мгновенно:
  на 75-й секунде GPU может стоять на нуле, а на 4-й минуте уже 100 % / 192 Вт.
- **`[datetime]::TryParse($s, [ref]$t)` в PS 5.1 падает** «Cannot find an overload for TryParse
  and the argument count 2», если `$t` не типизирована, а `Parse` на клиентской локали (uk-UA)
  жуёт `2026-08-11 13:03:34` по-своему. Разбирая время из чужих логов — только
  `[datetime]::ParseExact(..., 'yyyy-MM-dd HH:mm:ss', [Globalization.CultureInfo]::InvariantCulture)`
  в `try/catch` (`game-session-log.ps1`).
- **Привязку события к сессии не делать фиксированным окном.** Первая версия
  `game-session-log.ps1` считала вырубон «игровым», если он в 90 минутах от старта игры — и
  7,7-часовая сессия ушла в графу «вне игры», занизив связь. Интервал сессии считать по
  фактическим границам (`removed` / следующий старт / разумный потолок), а не по константе
  (бэклог п.138).
- **Скрипты для `szcli exec -f` писать инструментом Write, не heredoc'ом bash.** `cat > f <<'EOF'`
  в Git Bash **схлопывает `\` в `\`**, и регулярка вида `'(\Device\Harddisk\d+)'` приезжает
  на клиент сломанной: `Unrecognized escape sequence \H`. Отладка при этом уходит в PowerShell,
  хотя ломается на записи файла. Для устройств из событий вообще не парсить текст сообщения —
  брать `$_.Properties[0].Value` (бэклог п.143).
