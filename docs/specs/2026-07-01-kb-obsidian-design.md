# База знаний sz-diag — дизайн Obsidian-vault

> Дата: 2026-07-01. Статус: согласовано с пользователем.
> Уточняет и заменяет каркас `kb/` из
> [2026-07-01-sz-diag-phase1-design.md](2026-07-01-sz-diag-phase1-design.md).

## Цель

`kb/` — это Obsidian-vault: накопленная база знаний по сервисным заявкам (СЗ),
связанная в граф по заказам, компонентам и типам дефектов. Для переиспользования
опыта на будущих СЗ.

Контекст: сервис в основном собирает ПК (кастомные сборки), поэтому «устройство/модель»
второстепенно, а компоненты и типы дефектов — главное.

## Сущности (типы заметок)

- **СЗ** — сервисная заявка (ядро). Папка на СЗ + home-заметка.
- **Заказ** — номер заказа. Группирует СЗ; главная ось «история обращений по заказу».
- **Компоненты / детали** — например `[[Kingston A400 240GB]]`, `[[БП 500W]]`.
- **Типы дефектов** — например `[[Не стартует POST]]`, `[[Перегрев]]`.
- **Устройства / модели** — опционально, только для брендовых машин; у сборок не
  заполняется.

**Осознанно НЕ ведём:** клиента (не нужен), статус, даты открытия/закрытия, исполнителя
— чтобы не было ручной рутины.

## Связи

```
Заказ ──1:*── СЗ ──*:*── Компонент (замены)
                   ├─*:*── Тип дефекта
                   └─*:1── Устройство (опционально)
```

## Структура vault

```
kb/                        ← корень Obsidian-vault
  СЗ/
    156864/
      156864.md            ← home-заметка СЗ (узел графа): frontmatter + связи + резюме,
                             инлайн подтягивает request/findings/actions через ![[...]]
      request.md           ← дефект со слов клиента
      findings.md          ← что нашла диагностика
      actions.md           ← что заменили / сделали
      logs/                ← сырые выводы диагностики
  Заказы/     A-2025-0098.md
  Компоненты/ Kingston A400 240GB.md
  Дефекты/    Не стартует POST.md
  Устройства/ (опционально)
  _templates/  — шаблоны новых заметок (Templates / Templater)
  _attachments/
  MOC.md       — карта базы знаний (индексные Dataview-запросы)
```

Файлы `request/findings/actions` остаются раздельными (как решил пользователь), но
графовым узлом заявки выступает `156864.md`, чтобы СЗ была одним узлом, а не четырьмя.

## Frontmatter home-заметки СЗ

```yaml
---
сз: 156864
заказ:      "[[A-2025-0098]]"
дефект:     ["[[Не стартует POST]]"]
заменено:   ["[[Kingston A400 240GB]]"]
устройство: "[[Lenovo IdeaPad 3]]"   # опционально, у сборок не заполняем
дата:       2026-07-01               # дата записи, ЗАПОЛНЯЕТСЯ АВТОМАТИЧЕСКИ при создании
---
```

- `дата` — единственное временное поле, автозаполнение (шаблон Obsidian или hub при
  создании папки СЗ). Вручную не ведётся.
- Списочные поля (`дефект`, `заменено`) — массивы wikilink’ов, чтобы Dataview собирал
  связи.

## Dataview — целевые сценарии

- В заметке **заказа**: таблица всех СЗ по заказу = история обращений. (главный сценарий)
- В заметке **компонента**: по каким СЗ его меняли.
- В заметке **типа дефекта**: похожие случаи и что помогло.
- В `MOC.md`: «Последние СЗ», «Топ дефектов», «Что чаще всего меняем».

## Теги (опционально, поверх связей)

Лёгкая фасетизация как дополнение к wikilink’ам, не замена: например `#дефект/питание`.
Не обязательны — основной способ навигации — связи и Dataview.

## Шаблоны

`_templates/` с заготовками (готовый frontmatter + секции): «новая СЗ», «новый заказ»,
«новый компонент», «новый тип дефекта». Дата записи проставляется шаблоном.

## Приватность / git

Заметки Заказов и содержимое СЗ могут содержать данные клиентов → весь `kb/` в
`.gitignore`, в репозиторий не попадает. Синхронизация vault (если будет) — только
приватная.

## Влияние на Фазу 1

Каркас, который создаёт агент/hub при открытии СЗ, должен сразу быть этой формы:
папка `СЗ/<номер>/` + `<номер>.md` (home) с автозаполненной `дата` и заготовками
`request/findings/actions/logs/`. Наполнение и Dataview-запросы/шаблоны — Фаза 2.
