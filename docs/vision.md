# sz-diag — система удалённой диагностики клиентских машин по СЗ

> Статус: **черновик / идёт брейншторм дизайна**. Это фиксация замысла, не финальная
> спека. Финальная спека Фазы 1 будет отдельным документом после согласования.
> Дата фиксации: 2026-07-01.

## Проблема / контекст

Сервисный центр (Telemart). Клиентские машины приезжают на диагностику/ремонт и
физически стоят в локальной сети сервиса. Нужно диагностировать их с помощью Claude,
но:

- Claude НЕ ставится на машину клиента и НЕ линкует туда рабочий аккаунт.
- Машин несколько одновременно → нужно понимать, к какой именно машине обращаться.
- Каждая заявка имеет номер **СЗ** (сервисная заявка), напр. `156864`.

### Модель угроз (важно для дизайна)

- Клиентская машина — **наименее доверенное устройство** в локалке; часто приезжает
  именно потому, что заражена. Малварь на ней может украсть токен/подсунуть ложные
  данные диагностики.
- **Решение по безопасности:** Claude работает на **чистом сервисном боксе** под
  рабочим аккаунтом и дотягивается до клиентской машины **по сети (SSH/WinRM)**.
  Рабочий токен на больную машину не заезжает.
- Малварь может врать диагностике даже по SSH (руткиты) → достоверная проверка на
  заражение делается офлайн-скан / загрузкой с чистого носителя. Это отдельная задача.

## Подсистемы

1. **Агент на клиенте** — консольная прога, запускается на машине клиента:
   - оператор вводит номер СЗ (напр. `156864`);
   - открывает SSH-доступ: включает OpenSSH Server, правило firewall, сервисную
     учётку/ключ, `LocalAccountTokenFilterPolicy=1` (полный токен для локального
     админа при сетевом логоне);
   - регистрируется в центральном реестре (СЗ → IP/статус).
2. **Центральный реестр + CLI** — на хосте сервиса:
   - показывает, какие СЗ сейчас онлайн и статус подключения («светится 156864»);
   - хранит маппинг `СЗ → IP машины`, чтобы Claude знал, к кому идти по SSH.
3. **Диагностика через Claude по SSH** — обвязка вокруг готового SSH: оператор
   говорит «на СЗ 156864 дефект такой-то» → Claude делает диагностику на той машине.
   Отдельной постройки почти не требует — включается, как только есть маппинг из п.2.
4. **База знаний по СЗ** — папка на хосте, по каждой заявке: дефект (со слов клиента),
   что обнаружилось, что заменили. Для переиспользования на будущих СЗ.
5. **(будущее) Тест-раннер + отчёты** — прогон набора программ тестирования и
   генерация отчёта со скринами.

## Фазирование

- **Фаза 1 (ядро, проектируем сейчас):** агент (1) + реестр/CLI (2) + минимальная
  структура папок базы знаний (4). Это то, что делает весь SSH-workflow рабочим.
- **Фаза 2:** автоматизация записи в базу знаний — структурированные данные по
  дефекту/находкам/заменам, поиск по прошлым СЗ.
- **Фаза 3:** тест-раннер + отчёты со скринами.

## Что уже решено

- Топология: Claude на чистом боксе → SSH/WinRM в клиента (токен не на клиенте).
- По SSH в Windows доступно: реестр (r/w), логи событий, файлы, службы, процессы,
  задачи. Ограничение — нет GUI. Нюансы: нет интерактивного UAC (нужен полный токен
  через `LocalAccountTokenFilterPolicy`), `HKCU` в SSH-сессии — куст SSH-юзера, а не
  интерактивного (для правки куста клиента — `reg load`).
