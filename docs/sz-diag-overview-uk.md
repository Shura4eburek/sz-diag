# SZ Diag — як виглядає процес (пояснення для IT-відділу)

Система віддаленої діагностики клієнтських машин у сервісному центрі за номером
**СЗ** (сервісна заявка, напр. `159873`). Claude працює на чистому сервісному боксі
і дотягується до клієнтських машин по SSH, **не встановлюючись** на них.

## Проблема, яку вирішуємо

Клієнтські машини приходять із «плаваючими» дефектами (спонтанні ребути, BSOD,
артефакти). Тягати кожну до стенду й руками ганяти тести — довго. SZ Diag дозволяє
**діагностувати віддалено за номером СЗ**.

## Модель загроз (чому саме так)

Клієнтська машина — **найменш довірений** пристрій, часто вже заражена. Тому:

- робочий токен / облікові дані сервісу на неї **не заїжджають**;
- увесь доступ **тимчасовий** і **відкочується без слідів**, коли СЗ закривають;
- напрям завжди «клієнт тягне з хоста», а не навпаки.

## Хто є хто в схемі

- **Сервісний бокс (хост)** — чиста машина, де сидить Claude + `hub` + `szcli`.
  Звідси йде вся діагностика.
- **Hub** — центральний сервіс на хості. Тримає мапінг `СЗ → IP`, приймає heartbeat
  від агентів, роздає команди, збирає звіти.
- **Агент** — маленька консоль на клієнтській машині. Не інсталюється в систему;
  запускається, тимчасово відкриває SSH-доступ і реєструється під номером СЗ.
- **CLI (`szcli`)** — тонкий клієнт, показує які СЗ онлайн і ганяє команди.

## Як виглядає процес

1. **Приймання.** Клієнтській машині присвоюють номер СЗ (напр. `159873`).
2. **Підняття агента.** На клієнті запускають агент (через `Updater.exe` — сам
   знаходить hub і оновлюється). Агент **тимчасово** відкриває SSH (портативний
   sshd під SYSTEM, свої ключі), реєструється на hub під своїм СЗ.
3. **Онлайн.** У `szcli` видно: СЗ `159873` онлайн, ось її IP. Хост коннектиться
   по SSH.
4. **Діагностика.** `szcli diag run <СЗ>` — збирає структурований звіт (залізо /
   диски / SMART / події / ребути / WHEA). Для важких кейсів — стрес (OCCT Power) +
   лог сенсорів (LHM), доставка тулів по SMB-шарі з хоста.
5. **Висновок.** Складаємо діагноз, кладемо в базу знань (Obsidian-vault,
   українською): блок «Для клієнта» для колл-центру + технічний розбір. Копимо
   патерни «симптом → причина».
6. **Закриття СЗ.** Агент **відкочує весь доступ без слідів** — sshd, тимчасова
   обліковка, ключі, задачі. Машина йде до клієнта чистою.

## Що робить Claude (роль у процесі)

Claude — на **сервісному боксі**, не на клієнті. Роль:

- ганяти діагностику по SSH через готові команди, читати звіти;
- **інтерпретувати** дані — відрізнити реальну причину від «невинного свідка»
  (напр. `WdFilter.sys` у дампі — це часто симптом битої пам'яті, а не винуватець);
- підбирати наступний крок (який тест ганяти, що свапати для дискримінації);
- формулювати діагноз і писати висновок у базу знань;
- розвивати саму систему (агент, hub, аналізатор дампів).

## Живий приклад

СЗ **159873** — спонтанні ребути. Спершу думали БЖ. OCCT Power **відтворив** дефект
за хвилини (хоча 5 год RDR2 не змогли), почерк приладовий: темпи норм, обрив на піку,
WHEA / BSOD порожні. БЖ виключили свопом (новий вирубається так само), а зниження
пам'яті **6000 → 5600 прибрало вирубони**. Діагноз: **EXPO 6000 нестабільний на IMC
Ryzen 7500F**. Той самий висновок підтвердився на СЗ **160176** (інша плата).
Системний висновок пішов у базу: **на Zen4 без «X» занижати заводський XMP до 5600**.
