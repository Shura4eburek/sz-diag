# Бэклог улучшений (боли из живых сессий)

Список ведётся по факту: каждый пункт — это то, обо что **реально споткнулись** на живой СЗ,
а не «было бы неплохо». Формат: **боль** (что случилось) → **что сделать** → **критерий готовности**.

Источник текущей порции — сессия **2026-07-27** (СЗ 160306 «вимикається/перезавантажується» +
верификация замены проца на 159873).

## P0 — бьёт каждый выезд

### 1. Доставка файлов на клиента через hub по HTTP (`szcli push`)

**Боль.** На 160306 доставка стресс-тулов встала колом почти на час. SMB не поднялся **ничем**:
ни по IP, ни по имени хоста, ни из SSH-сессии, ни из scheduled task под SYSTEM — везде
`System error 67 (ERROR_BAD_NET_NAME)`, при том что порт 445 доступен, шара настроена верно
(`ScopeName=*`, Everyone+`MAMORU\1` Full), а с самого хоста открывается. Тулы доехали только
через **временную HTTP-раздачу питоном**, поднятую руками.

⚠️ **Уточнение диагноза (2026-07-28).** Сначала повесили вину на антивирус клиента
(`360netmon` у 360 Total Security). Оказалось **неверно**: на 160467, где стоит только Windows
Defender и никаких сторонних AV, SMB даёт **тот же error 67**. То есть виновата **сторона хоста**:
на нём одновременно активны openvpn / Pritunl / Surfshark / Tailscale / ZeroTier, и kill switch
VPN (Surfshark/Pritunl) рубит входящий локальный трафик через WFP — TCP на 445 открывается,
а SMB tree connect не проходит. `Get-SmbSession` на хосте при попытках пуст.

Вывод: **SMB как транспорт доставки принципиально ненадёжен** — он зависит от VPN/фаерволов/AV
на обеих сторонах. HTTP-канал до hub при этом работает всегда (агент же держит с ним связь).

**Что сделать.** Раздавать инструменты **через hub**, тем же каналом, который уже гарантированно
работает (агент же держит с hub SignalR + апдейтер качает пакет по HTTP):
- эндпоинт раздачи в hub по аналогии с `AgentPackageApi` (`src/SzDiag.Hub/AgentPackageApi.cs`):
  `GET /tools/list`, `GET /tools/{name}` из папки `client-tools`, аутентификация тем же
  `X-SzDiag-Token`, sha256 рядом;
- команда `szcli push <СЗ> <tool>` → hub шлёт агенту команду, **агент сам качает** с hub и кладёт
  в свою рабочую папку (клиент тянет с хоста — ровно как в модели угроз);
- прогресс/ошибка возвращаются в CLI.

**Критерий готовности.** `szcli push 160306 occt` кладёт OCCT на клиента с антивирусом на борту,
без SMB, без ручных серверов, с проверкой sha256.

### 2. Ad-hoc PowerShell на клиенте через агента (`szcli exec`)

**Боль.** Вся разведка шла через `ssh + powershell -EncodedCommand`, и это минное поле:
- `Access is denied` на ровном месте (оказалось — антивирус, но я час подозревал длину команды
  и права, и делал бинарный поиск лимита);
- вывод засран **CLIXML** — `Write-Host` через non-interactive SSH сериализуется, приходится
  фильтровать `grep -vE "CLIXML|<Objs"`; спасает только `[Console]::Out.WriteLine`;
- локаль: `{0:N1}` печатает запятую и nbsp → парсинг ломается, нужен явный `InvariantCulture`;
- токен SSH-сессии имеет `NT AUTHORITY\NETWORK` → сетевые операции (SMB) из неё не работают;
- под нагрузкой sshd **глохнет** (`banner exchange timeout`), и связь пропадает именно тогда,
  когда данные нужнее всего;
- ConPTY не тянет ввод (заливка файла невозможна), а длинные скрипты приходится дробить.

**Что сделать.** Агент уже умеет `RunDiag` — обобщить до «выполни PS-скрипт и верни stdout»:
- команда hub→агент `Exec` (скрипт + таймаут), результат возвращается через тот же канал;
- на стороне агента — запуск локально (полные права, без ConPTY, без network-токена);
- `szcli exec <СЗ> -f script.ps1` / `szcli exec <СЗ> "..."`.

**Критерий готовности.** Сбор логов/сенсоров/железа не требует SSH вообще; работает под полной
нагрузкой, когда sshd мёртв (агент отвечает — heartbeat же идёт).

### 3. ✅ СДЕЛАНО (2026-07-28) — boot-time от агента → отличать вырубон от лага

**Боль.** За одну сессию **трижды** не смог однозначно ответить «машина вырубилась или связь
лагает»:
- под OCCT sshd глохнет, hub метит СЗ `offline` — а машина жива (heartbeat просто опаздывает);
- в конце прогона: hub `offline` + **ping отвечает** + SSH молчит → отличить «ребут» от
  «задушена нагрузкой» стало нечем, потому что после ребута наши sshd/агент не автостартуют
  (на клиенте оказался билд 23.07, до resume-механики);
- на 159873 та же эвристика («SSH ответил = вырубилась») подводила дважды.

**Что сделать.** (Направление уже записано в CLAUDE.md — сессия подтвердила приоритет.)
- агент шлёт в heartbeat `LastBootUpTime`;
- hub хранит и различает: **boot-time сменился → реальный ребут** (и фиксирует «продержался N
  минут под тестом»); **boot тот же, heartbeat опоздал → лаг, машина жива**;
- `szcli list` — колонка uptime/boot; авто-таймлайн вырубонов по СЗ.

**Критерий готовности.** Во время стресс-теста CLI честно показывает «жива, heartbeat лагает»
против «вырубилась в HH:MM, продержалась N минут», без ручного гадания по ssh/ping.

**Как сделано.** Boot-time уехал не в heartbeat, а в **`Register`** — он не меняется, пока машина
не перезагрузилась, поэтому гонять его каждые 20 секунд незачем, а после ребута агент стартует
заново и присылает новый. Бонус: heartbeat не тронут → протокол остался обратно совместимым.

- `RegisterRequest.BootTime` / `SessionInfo.BootTime` + `LastRebootAt` (оба nullable);
- `BootTimeReader` на агенте — читает `Win32_OperatingSystem.LastBootUpTime` **один раз** при
  старте. Намеренно без фоллбэка на `Environment.TickCount64`: тот не идёт во время сна, и после
  пробуждения дал бы **ложный ребут**. Не смогли прочитать → `null` («неизвестно»);
- `SessionRegistry.Register` сравнивает старый и новый boot-time → выставляет `LastRebootAt` и
  возвращает флаг; `AgentHub` пишет в консоль «клиент перезагрузился»;
- `szcli list/watch` — колонка **Uptime**, свежий ребут (< 1 ч) подсвечен красным с временем;
- 17 тестов, в т.ч. на отсутствие ложных срабатываний: одинаковый boot-time при
  переподключении ≠ ребут, `null` от старого агента ≠ ребут.

**Осталось (не блокирует):** фиксировать «продержался N минут под тестом» в истории СЗ и
авто-таймлайн вырубонов — сейчас видно только текущее состояние.

⚠️ До клиентов доедет **только после `build-dist`** (см. п.4) — старые агенты boot-time не шлют,
и колонка у них будет пустой.

## P1 — режет время и путает выводы

### 4. Гарантия, что фича доезжает до клиента (freshness guard для `build-dist`)

**Боль.** Механику «агент переживает ребут» (`--resume` + автостарт-таск) сделали **24.07**, а на
клиенте 160306 стоял агент от **23.07 17:55** — без неё. Причина не в апдейтере: он честно
качает с hub, но в `dist\host\hub\agent-dist\package.zip` лежала сборка от 23.07 —
**`build-dist.ps1` после фичи ни разу не гоняли**. То есть фича физически не доезжала **ни до
одного** клиента, и обнаружилось это случайно, посреди диагностики.

**Что сделать.**
- `szcli doctor` (или проверка при старте hub): сравнить дату/коммит `agent-dist/version.txt` с
  последним коммитом, трогавшим `src/SzDiag.Agent*` → предупредить «пакет агента устарел на N
  коммитов, прогони build-dist»;
- в идеале — pre-push хук или CI-шаг.

**Критерий готовности.** Забыть пересобрать dist после правки агента невозможно молча — CLI/hub
об этом говорит.

### 5. `szcli diag`: валидация секций и обратная связь по ошибке

**Боль.** Две подряд:
- невалидные имена секций **молча игнорируются**: `szcli diag run 160306 hw memory reboots whea`
  → CLI ответил «секции: hw», а собралась одна `system`. Имена `hw`/`reboots`/`whea` не
  существуют, но никто не сказал;
- разделитель — **запятая**, а пробел молча режет всё после первого аргумента;
- запуск на 160306 **вообще не дал отчёта** (вероятно, агента прибил антивирус) — и об этом
  никто не сообщил: CLI отрапортовал «диагностика запущена», а `reports/` так и остался пуст.
  Ждал вслепую, потом плюнул и ушёл собирать всё руками по SSH.

**Что сделать.**
- валидировать имена секций, при опечатке — ошибка со списком допустимых (+ алиасы `hw`→`system`,
  `reboots`/`whea`→`reliability`, и `all`);
- принимать и запятые, и несколько аргументов через пробел; эхом печатать реальный список;
- агент репортит статус выполнения (started/failed + текст ошибки) → `szcli diag status <СЗ>`,
  таймаут с внятным сообщением вместо тишины.

**Критерий готовности.** Опечатка в секции — видимая ошибка; упавшая диагностика — видимая
причина, а не пустая папка.

### 6. Сенсоры одной командой (`szcli sensors …`)

**Боль.** Ритуал повторяется на каждой СЗ вручную: доставить `lhmmon` → написать `run.cmd` →
создать scheduled task под SYSTEM → запустить → **не забыть остановить** (пока задача жива, файл
залочен и построчное чтение молча даёт 0 строк — на это уже наступал) → забрать CSV → **каждый
раз заново писать PowerShell-парсер** для max/avg.

**Что сделать.**
- `szcli sensors start|stop <СЗ>` — агент сам ставит/снимает задачу под SYSTEM, пишет CSV 1/с;
- `szcli sensors pull <СЗ>` — забрать CSV на хост;
- `szcli sensors report <csv>` — готовая сводка: max/avg/min по ключевым (CPU/GPU power, temp,
  clock, load), **детект обрыва** (последняя секунда перед пропажей данных) и — важное —
  **сколько времени реально держалась нагрузка**.

**Почему последнее критично.** На 160306 первый прогон выглядел как «40 минут выстояла», а по CSV
оказалось: комбинированная нагрузка шла **4.2 минуты**, остальные 23 минуты машина простаивала
(OCCT отработал конечное расписание и вышел). Без пересчёта по CSV вывод был бы неверным.

**Критерий готовности.** Снятие и разбор сенсоров — две команды, а «была ли нагрузка настоящей»
видно в отчёте автоматически.

## P2 — полезное, но терпит

### 7. Снимать напряжения памяти и VSOC (критично для AM5)

**Боль.** По кейсам 7500F+DDR5-6000 ([[159873]], [[160176]], [[160450]], [[160467]]) мы делаем
выводы про EXPO, но **напряжения не снимаем вообще**. В `diag`-секции memory есть только
`Speed`/`ConfiguredClockSpeed`. Из-за этого:
- не видно, включён ли профиль, когда частоты совпадают (на 160467 `Speed=Configured=4800` —
  по ним не понять, был ли EXPO; а `ConfiguredVoltage=1100` сразу говорит «сток»);
- не видно **VSOC**, а именно он убивает Zen4 (AMD не зря загнала лимит 1.3 В в AGESA). Если
  плата на EXPO 6000 выставляет VSOC под 1.3+, то «дохлый экземпляр 7500F» — это не невезение,
  а закономерная деградация, и вывод по всей серии сборок другой.

**Что сделать.**
- в секцию `memory` добавить `ConfiguredVoltage` / `MinVoltage` / `MaxVoltage` из
  `Win32_PhysicalMemory` (дёшево, уже доступно — 1.1 В = JEDEC, 1.35–1.4 В = EXPO/XMP);
- для AM5 снимать **VSOC** через `lhmmon` (LHM отдаёт `Voltage|SoC (SVI2 TFN)` и
  `Voltage|Core (SVI2 TFN)`) — и класть в отчёт рядом с частотой;
- в идеале — фиксировать VSOC, который плата ставит **автоматом при включении EXPO**, чтобы
  накопить статистику по моделям плат.

⚠️ Важно: `lhmmon` нельзя гонять параллельно с OCCT — конфликт за ring0, CPU-сенсоры читаются
нулями (ловили на 159873). Снимать напряжения **до** стресса либо отдельным заходом.

🚨 **Блокер (2026-07-28): `lhmmon` слепнет на машинах с HVCI.** Попытка снять VSOC на 160467
(AM5, 7500F) дала `Core VID` и больше ничего: частоты `NaN`, `Tctl=0`, SVI2-сенсоров нет.
Причина — **Memory Integrity (HVCI) включён** (`VBS=2`, `SecurityServicesRunning=2`) + активна
Microsoft Windows Driver Policy, а наш `lhmmon` построен на **WinRing0**, который в блок-листе
уязвимых драйверов. Подтверждено сравнением: на 160306 `VBS=0` — те же сенсоры читаются штатно.

На свежих установках Win11 24H2+ Memory Integrity включена **по умолчанию** → проблема будет
только расти. Именно из-за этого HWiNFO ушёл на **PawnIO** (видели его на 161100, где он ломал
запуск FACEIT).

**Варианты:** (а) пересобрать `lhmmon` на LibreHardwareMonitor с поддержкой **PawnIO** вместо
WinRing0 — правильный путь; (б) временно гасить Memory Integrity на клиенте (вмешательство +
ребут, для клиентской машины плохо); (в) VSOC смотреть глазами в BIOS (не автоматизируется).
Пока не сделано (а) — в отчёте честно писать «сенсоры недоступны: HVCI», а не молча выдавать нули.

**Критерий готовности.** По `diag.md` видно, включён ли профиль памяти и какой VSOC — без
захода в BIOS и без ручных тулов.

### 9. `szcli kb doctor` — проверка целостности vault

**Боль.** В заметке СЗ **160467** отображался вывод по **159794**. Данные не путались: скелет
содержит `![[висновок]]`, а сам `висновок.md` при создании СЗ **не создавался** (его писал только
`EnsureSummarySkeleton` при записи вывода). Obsidian разрешает короткие ссылки по всему vault и
подставляет первый попавшийся файл с тем же именем — так в СЗ уезжает **чужой вывод**. Выглядит
как порча данных, ищется долго. Затронуто было 3 СЗ (159558, 160306, 160467).
Починено (скелет создаёт заготовку + `EnsureSkeleton` стал самовосстанавливающимся), но сам
класс проблемы шире.

**Что сделать.** Команда проверки vault: висячие эмбеды/ссылки (`![[x]]` без файла в своей папке),
дубли имён файлов между СЗ, СЗ без обязательных файлов, битые `[[...]]` на несуществующие
паттерны/сущности. Плюс опция `--fix` для дозаполнения скелетов.

**Критерий готовности.** «Чужой вывод в чужой СЗ» ловится командой, а не глазами через неделю.

## Замечания по процессу (без кода)

- **Антивирус на клиенте — первый подозреваемый при «странностях» диагностики.** На 160306
  360 Total Security: резал PowerShell-вызовы (`Access is denied`), рубил SMB, вероятно прибил
  RunDiag. Стоит первым делом проверять сторонний AV и фиксировать его в `діагностика.md`
  (сейчас это сделано вручную).
- **Снос AV с самозащитой — только через Safe Mode**, и обязательно `sc delete` служб/драйверов
  **до** удаления файлов: у 360 есть ELAM boot-start драйвер (`360elam64`), и снос файлов без
  снятия регистрации грозит незагрузкой. На диагностируемой машине с вырубонами это риск
  создать артефакт и запутать диагноз.
