# Бэклог улучшений (боли из живых сессий)

Список ведётся по факту: каждый пункт — это то, обо что **реально споткнулись** на живой СЗ,
а не «было бы неплохо». Формат: **боль** (что случилось) → **что сделать** → **критерий готовности**.

Источник текущей порции — сессия **2026-07-27** (СЗ 160306 «вимикається/перезавантажується» +
верификация замены проца на 159873).

## P0 — бьёт каждый выезд

### 1. Доставка файлов на клиента через hub по HTTP (`szcli push`)

**Боль.** На 160306 доставка стресс-тулов встала колом почти на час. SMB не поднялся **ничем**:
ни по IP, ни по имени хоста, ни из SSH-сессии, ни из scheduled task под SYSTEM — везде
`System error 67 (ERROR_BAD_NET_NAME)`, при том что порт 445 доступен, шара настроена верно
(`ScopeName=*`, Everyone+`MAMORU\1` Full), а с самого хоста открывается. Тулы доехали только
через **временную HTTP-раздачу питоном**, поднятую руками.

⚠️ **Уточнение диагноза (2026-07-28).** Сначала повесили вину на антивирус клиента
(`360netmon` у 360 Total Security). Оказалось **неверно**: на 160467, где стоит только Windows
Defender и никаких сторонних AV, SMB даёт **тот же error 67**. То есть виновата **сторона хоста**:
на нём одновременно активны openvpn / Pritunl / Surfshark / Tailscale / ZeroTier, и kill switch
VPN (Surfshark/Pritunl) рубит входящий локальный трафик через WFP — TCP на 445 открывается,
а SMB tree connect не проходит. `Get-SmbSession` на хосте при попытках пуст.

Вывод: **SMB как транспорт доставки принципиально ненадёжен** — он зависит от VPN/фаерволов/AV
на обеих сторонах. HTTP-канал до hub при этом работает всегда (агент же держит с ним связь).

**Что сделать.** Раздавать инструменты **через hub**, тем же каналом, который уже гарантированно
работает (агент же держит с hub SignalR + апдейтер качает пакет по HTTP):
- эндпоинт раздачи в hub по аналогии с `AgentPackageApi` (`src/SzDiag.Hub/AgentPackageApi.cs`):
  `GET /tools/list`, `GET /tools/{name}` из папки `client-tools`, аутентификация тем же
  `X-SzDiag-Token`, sha256 рядом;
- команда `szcli push <СЗ> <tool>` → hub шлёт агенту команду, **агент сам качает** с hub и кладёт
  в свою рабочую папку (клиент тянет с хоста — ровно как в модели угроз);
- прогресс/ошибка возвращаются в CLI.

**Критерий готовности.** `szcli push 160306 occt` кладёт OCCT на клиента с антивирусом на борту,
без SMB, без ручных серверов, с проверкой sha256.

### 2. ✅ СДЕЛАНО (2026-07-28) — ad-hoc PowerShell через агента (`szcli exec`)

**Боль.** Вся разведка шла через `ssh + powershell -EncodedCommand`, и это минное поле:
- `Access is denied` на ровном месте (оказалось — антивирус, но я час подозревал длину команды
  и права, и делал бинарный поиск лимита);
- вывод засран **CLIXML** — `Write-Host` через non-interactive SSH сериализуется, приходится
  фильтровать `grep -vE "CLIXML|<Objs"`; спасает только `[Console]::Out.WriteLine`;
- локаль: `{0:N1}` печатает запятую и nbsp → парсинг ломается, нужен явный `InvariantCulture`;
- токен SSH-сессии имеет `NT AUTHORITY\NETWORK` → сетевые операции (SMB) из неё не работают;
- под нагрузкой sshd **глохнет** (`banner exchange timeout`), и связь пропадает именно тогда,
  когда данные нужнее всего;
- ConPTY не тянет ввод (заливка файла невозможна), а длинные скрипты приходится дробить.

**Что сделать.** Агент уже умеет `RunDiag` — обобщить до «выполни PS-скрипт и верни stdout»:
- команда hub→агент `Exec` (скрипт + таймаут), результат возвращается через тот же канал;
- на стороне агента — запуск локально (полные права, без ConPTY, без network-токена);
- `szcli exec <СЗ> -f script.ps1` / `szcli exec <СЗ> "..."`.

**Критерий готовности.** Сбор логов/сенсоров/железа не требует SSH вообще; работает под полной
нагрузкой, когда sshd мёртв (агент отвечает — heartbeat же идёт).

**Как сделано.** Request/response поверх SignalR (обычные команды агенту fire-and-forget, а exec
обязан вернуть вывод вызвавшему):

```
szcli exec <СЗ> "<script>" [--timeout N]   |   szcli exec <СЗ> -f script.ps1
   → POST /api/sessions/{sz}/exec
   → ExecCoordinator: заводит RequestId + TaskCompletionSource, шлёт агенту Exec
   → агент: ExecCommandHandler запускает PowerShell локально
   → агент: ExecResult(RequestId, …) обратно на hub
   → координатор будит ожидающий запрос → JSON в CLI
```

- `ExecRequest` / `ExecResult` / `ExecCommandRequest` + `ExecLimits` в Contracts;
- вывод режется на **200 000 символов** с флагом `Truncated` (SignalR-сообщение ограничено);
- таймаут скрипта убивает процесс на агенте (`TimedOut`), hub ждёт с запасом `HubGraceSeconds`,
  иначе сдавался бы ровно тогда, когда агент собирается ответить; CLI ждёт дольше hub — иначе
  вместо честного 504 вылезал бы `TaskCanceledException`;
- **обработчик на агенте никогда не бросает**: таймаут, ненулевой exit code и даже «powershell не
  найден» уходят ответом. Молчание агента вызывающий не отличил бы от потери связи;
- ненулевой exit code — валидный результат, а не сбой: `throwOnError: false`;
- 12 тестов (координатор: сопоставление по RequestId, таймаут без утечки pending, ответ на чужой
  RequestId игнорируется; обработчик: обрезка, таймаут, дефолтный таймаут, ошибки).

**Что это даёт:** сбор данных больше не зависит от SSH — уходят `Access denied` от антивируса,
CLIXML в выводе, локаль с запятыми, network-токен `NT AUTHORITY\NETWORK` и главное — смерть sshd
под нагрузкой. Также это предпосылка для п.1 (доставка) и для отказа от учётки `svc-diag`
в автозапуске.

**Осталось:** живая проверка на онлайн-СЗ (все машины были offline на момент реализации).

### 3. ✅ СДЕЛАНО (2026-07-28) — boot-time от агента → отличать вырубон от лага

**Боль.** За одну сессию **трижды** не смог однозначно ответить «машина вырубилась или связь
лагает»:
- под OCCT sshd глохнет, hub метит СЗ `offline` — а машина жива (heartbeat просто опаздывает);
- в конце прогона: hub `offline` + **ping отвечает** + SSH молчит → отличить «ребут» от
  «задушена нагрузкой» стало нечем, потому что после ребута наши sshd/агент не автостартуют
  (на клиенте оказался билд 23.07, до resume-механики);
- на 159873 та же эвристика («SSH ответил = вырубилась») подводила дважды.

**Что сделать.** (Направление уже записано в CLAUDE.md — сессия подтвердила приоритет.)
- агент шлёт в heartbeat `LastBootUpTime`;
- hub хранит и различает: **boot-time сменился → реальный ребут** (и фиксирует «продержался N
  минут под тестом»); **boot тот же, heartbeat опоздал → лаг, машина жива**;
- `szcli list` — колонка uptime/boot; авто-таймлайн вырубонов по СЗ.

**Критерий готовности.** Во время стресс-теста CLI честно показывает «жива, heartbeat лагает»
против «вырубилась в HH:MM, продержалась N минут», без ручного гадания по ssh/ping.

**Как сделано.** Boot-time уехал не в heartbeat, а в **`Register`** — он не меняется, пока машина
не перезагрузилась, поэтому гонять его каждые 20 секунд незачем, а после ребута агент стартует
заново и присылает новый. Бонус: heartbeat не тронут → протокол остался обратно совместимым.

- `RegisterRequest.BootTime` / `SessionInfo.BootTime` + `LastRebootAt` (оба nullable);
- `BootTimeReader` на агенте — читает `Win32_OperatingSystem.LastBootUpTime` **один раз** при
  старте. Намеренно без фоллбэка на `Environment.TickCount64`: тот не идёт во время сна, и после
  пробуждения дал бы **ложный ребут**. Не смогли прочитать → `null` («неизвестно»);
- `SessionRegistry.Register` сравнивает старый и новый boot-time → выставляет `LastRebootAt` и
  возвращает флаг; `AgentHub` пишет в консоль «клиент перезагрузился»;
- `szcli list/watch` — колонка **Uptime**, свежий ребут (< 1 ч) подсвечен красным с временем;
- 17 тестов, в т.ч. на отсутствие ложных срабатываний: одинаковый boot-time при
  переподключении ≠ ребут, `null` от старого агента ≠ ребут.

**Осталось (не блокирует):** фиксировать «продержался N минут под тестом» в истории СЗ и
авто-таймлайн вырубонов — сейчас видно только текущее состояние.

⚠️ До клиентов доедет **только после `build-dist`** (см. п.4) — старые агенты boot-time не шлют,
и колонка у них будет пустой.

## P1 — режет время и путает выводы

### 4. Гарантия, что фича доезжает до клиента (freshness guard для `build-dist`)

**Боль.** Механику «агент переживает ребут» (`--resume` + автостарт-таск) сделали **24.07**, а на
клиенте 160306 стоял агент от **23.07 17:55** — без неё. Причина не в апдейтере: он честно
качает с hub, но в `dist\host\hub\agent-dist\package.zip` лежала сборка от 23.07 —
**`build-dist.ps1` после фичи ни разу не гоняли**. То есть фича физически не доезжала **ни до
одного** клиента, и обнаружилось это случайно, посреди диагностики.

**Что сделать.**
- `szcli doctor` (или проверка при старте hub): сравнить дату/коммит `agent-dist/version.txt` с
  последним коммитом, трогавшим `src/SzDiag.Agent*` → предупредить «пакет агента устарел на N
  коммитов, прогони build-dist»;
- в идеале — pre-push хук или CI-шаг.

**Критерий готовности.** Забыть пересобрать dist после правки агента невозможно молча — CLI/hub
об этом говорит.

> Связано с п.5: guard только **предупреждает**, а push-обновление реально **доставляет**. Если
> делать оба — этот пункт становится страховкой на случай, когда агент офлайн и push не дошёл.

### 5. Обновление без даунтайма: hub переживает пересборку, агент ловит обнову сам

**Боль.** Выкатка любой правки — ручной ритуал: убить hub → собрать → обойти залочку (см. п.9) →
поднять заново. За один вечер 28.07 делали это дважды, и **оба раза** `build-dist` не смог
заменить exe сам. Пока hub лежит, все СЗ отваливаются в offline; если в этот момент идёт
стресс-тест — теряем и связь, и наблюдение ровно тогда, когда оно нужно.

Со стороны агента симметрично: он подтягивает пакет **только при своём запуске**. Из-за этого
resume-механика, сделанная 24.07, доехала до клиентов лишь 28.07 — четыре дня жила в репозитории
и ни на одной машине не работала.

**Что сделать.**
1. **Hub переживает обновление сам.** Приостановить приём (drain текущих запросов), подменить
   бинарь, перезапуститься, поднять соединения — без ручного kill и без закрытия окна.
   Реализация на выбор: супервизор-лаунчер (`start-hub.cmd` следит за процессом и перезапускает
   его после подмены) либо self-update отдельным процессом. Побочно чинит п.9: подменяет не
   скрипт сборки, а сам сервис в момент, когда файлы уже свободны.
2. **Push обновления агенту.** Hub после `build-dist` рассылает «вышла версия X»; агент, **если
   ничем не занят** (`Activity == готов`, нет активного теста/диагностики), сам качает пакет и
   перезапускается через `SzDiag.Updater`. Занят — откладывает до конца прогона.
   Это радикальнее, чем freshness-guard из п.4: тот только предупреждает, а push реально доставляет.
3. **Никогда не обновляться под нагрузкой** — перезапуск агента посреди стресс-теста убьёт и
   тест, и логгер сенсоров. Активность агента уже известна hub (`ReportActivity`), её и проверять.

**Критерий готовности.** Выкатка новой сборки не требует ручного kill hub и не роняет активные
СЗ; агент, стоящий без дела, подтягивает свежую версию в течение нескольких минут после
`build-dist` — сам, без переустановки и без визита к машине.

### 6. `szcli diag`: валидация секций и обратная связь по ошибке

**Боль.** Две подряд:
- невалидные имена секций **молча игнорируются**: `szcli diag run 160306 hw memory reboots whea`
  → CLI ответил «секции: hw», а собралась одна `system`. Имена `hw`/`reboots`/`whea` не
  существуют, но никто не сказал;
- разделитель — **запятая**, а пробел молча режет всё после первого аргумента;
- запуск на 160306 **вообще не дал отчёта** (вероятно, агента прибил антивирус) — и об этом
  никто не сообщил: CLI отрапортовал «диагностика запущена», а `reports/` так и остался пуст.
  Ждал вслепую, потом плюнул и ушёл собирать всё руками по SSH.

**Что сделать.**
- валидировать имена секций, при опечатке — ошибка со списком допустимых (+ алиасы `hw`→`system`,
  `reboots`/`whea`→`reliability`, и `all`);
- принимать и запятые, и несколько аргументов через пробел; эхом печатать реальный список;
- агент репортит статус выполнения (started/failed + текст ошибки) → `szcli diag status <СЗ>`,
  таймаут с внятным сообщением вместо тишины.

**Критерий готовности.** Опечатка в секции — видимая ошибка; упавшая диагностика — видимая
причина, а не пустая папка.

### 7. Сенсоры одной командой (`szcli sensors …`)

**Боль.** Ритуал повторяется на каждой СЗ вручную: доставить `lhmmon` → написать `run.cmd` →
создать scheduled task под SYSTEM → запустить → **не забыть остановить** (пока задача жива, файл
залочен и построчное чтение молча даёт 0 строк — на это уже наступал) → забрать CSV → **каждый
раз заново писать PowerShell-парсер** для max/avg.

**Что сделать.**
- `szcli sensors start|stop <СЗ>` — агент сам ставит/снимает задачу под SYSTEM, пишет CSV 1/с;
- `szcli sensors pull <СЗ>` — забрать CSV на хост;
- `szcli sensors report <csv>` — готовая сводка: max/avg/min по ключевым (CPU/GPU power, temp,
  clock, load), **детект обрыва** (последняя секунда перед пропажей данных) и — важное —
  **сколько времени реально держалась нагрузка**.

**Почему последнее критично.** На 160306 первый прогон выглядел как «40 минут выстояла», а по CSV
оказалось: комбинированная нагрузка шла **4.2 минуты**, остальные 23 минуты машина простаивала
(OCCT отработал конечное расписание и вышел). Без пересчёта по CSV вывод был бы неверным.

**Критерий готовности.** Снятие и разбор сенсоров — две команды, а «была ли нагрузка настоящей»
видно в отчёте автоматически.

## P2 — полезное, но терпит

### 8. Снимать напряжения памяти и VSOC (критично для AM5)

**Боль.** По кейсам 7500F+DDR5-6000 ([[159873]], [[160176]], [[160450]], [[160467]]) мы делаем
выводы про EXPO, но **напряжения не снимаем вообще**. В `diag`-секции memory есть только
`Speed`/`ConfiguredClockSpeed`. Из-за этого:
- не видно, включён ли профиль, когда частоты совпадают (на 160467 `Speed=Configured=4800` —
  по ним не понять, был ли EXPO; а `ConfiguredVoltage=1100` сразу говорит «сток»);
- не видно **VSOC**, а именно он убивает Zen4 (AMD не зря загнала лимит 1.3 В в AGESA). Если
  плата на EXPO 6000 выставляет VSOC под 1.3+, то «дохлый экземпляр 7500F» — это не невезение,
  а закономерная деградация, и вывод по всей серии сборок другой.

**Что сделать.**
- в секцию `memory` добавить `ConfiguredVoltage` / `MinVoltage` / `MaxVoltage` из
  `Win32_PhysicalMemory` (дёшево, уже доступно — 1.1 В = JEDEC, 1.35–1.4 В = EXPO/XMP);
- для AM5 снимать **VSOC** через `lhmmon` (LHM отдаёт `Voltage|SoC (SVI2 TFN)` и
  `Voltage|Core (SVI2 TFN)`) — и класть в отчёт рядом с частотой;
- в идеале — фиксировать VSOC, который плата ставит **автоматом при включении EXPO**, чтобы
  накопить статистику по моделям плат.

⚠️ Важно: `lhmmon` нельзя гонять параллельно с OCCT — конфликт за ring0, CPU-сенсоры читаются
нулями (ловили на 159873). Снимать напряжения **до** стресса либо отдельным заходом.

🚨 **Блокер (2026-07-28): `lhmmon` слепнет на машинах с HVCI.** Попытка снять VSOC на 160467
(AM5, 7500F) дала `Core VID` и больше ничего: частоты `NaN`, `Tctl=0`, SVI2-сенсоров нет.
Причина — **Memory Integrity (HVCI) включён** (`VBS=2`, `SecurityServicesRunning=2`) + активна
Microsoft Windows Driver Policy, а наш `lhmmon` построен на **WinRing0**, который в блок-листе
уязвимых драйверов. Подтверждено сравнением: на 160306 `VBS=0` — те же сенсоры читаются штатно.

На свежих установках Win11 24H2+ Memory Integrity включена **по умолчанию** → проблема будет
только расти. Именно из-за этого HWiNFO ушёл на **PawnIO** (видели его на 161100, где он ломал
запуск FACEIT).

**Варианты:** (а) пересобрать `lhmmon` на LibreHardwareMonitor с поддержкой **PawnIO** вместо
WinRing0 — правильный путь; (б) временно гасить Memory Integrity на клиенте (вмешательство +
ребут, для клиентской машины плохо); (в) VSOC смотреть глазами в BIOS (не автоматизируется).
Пока не сделано (а) — в отчёте честно писать «сенсоры недоступны: HVCI», а не молча выдавать нули.

**Критерий готовности.** По `diag.md` видно, включён ли профиль памяти и какой VSOC — без
захода в BIOS и без ручных тулов.

### 9. `build-dist`: hub не пересобирается из-за залоченной папки

**Боль (2026-07-28).** Прогон `build-dist` дважды подряд дал `ПРОПУСК src/SzDiag.Hub: собрано в
dist/host/hub.new, но dist/host/hub залочен` — **притом что все процессы SzDiag были остановлены**
(проверено: `Get-Process SzDiag*` пуст). Скорее всего свежий 97-мегабайтный exe держал антивирус
после публикации. Скрипт при этом честно отработал остальное, но hub остался старой версии — то
есть фикс/фича в hub молча не доезжает до рантайма, а по логу это выглядит как «готово частично».

Обошли вручную: скопировали содержимое `hub.new` поверх `hub`, **кроме `appsettings.json`** — в

**Что сделать.**
- в `build-dist`: если rename не удался — не сдаваться, а **копировать файлы поверх** (кроме

**Критерий готовности.** `build-dist` либо доводит сборку до конца, либо громко говорит «hub НЕ
обновлён», и ни при каком исходе не может затереть пути к `kb`/`szdiag.db`.

### 16. WinPE-флешка: агент в среде без установленной ОС

**Контекст (2026-07-29).** Сделан `tools/build-winpe.ps1` + режим `agent.exe --pe`
(`WinPeAccessManager` — no-op доступ: в PE нет SAM/Task Scheduler/фаервола, а `X:` это RAM-диск,
следов не остаётся by design). Даёт то, чего раньше не могли вообще: диагностику машины,
**которая не грузится**, чистую среду без малвари и offline-разбор винды клиента (EVTX/минидампы/
реестр прямо с диска).

**Грабли, зафиксировать чтобы не наступить снова:**
- **В `boot.wim` с установочной флешки винды нет PowerShell** (нет `WinPE-PowerShell`/`WinPE-WMI`/
  `WinPE-NetFx`) — а вся наша диагностика на нём. Поэтому образ строится с нуля из ADK, а не
  правкой установочного носителя.
- Пакеты ставятся в порядке зависимостей: WMI → NetFx → Scripting → PowerShell, каждый со своей
  `en-us` парой.
- Single-file .NET распаковывается во временную папку: RAM-диску нужен `/Set-ScratchSpace:512`
  либо `DOTNET_BUNDLE_EXTRACT_BASE_DIR` на флешку (в скрипте — второе).
- Агент лежит **на флешке**, не в `boot.wim`: обновление = копирование файла, без пересборки.
- **`reg load` в exec-скрипте может не выгрузиться и заблокировать DISM.** На 160450 скрипт
  читал версию ОС из offline-куста (`reg load HKLM\OFFSOFT ...\config\SOFTWARE`), а `reg unload`
  в `finally` упал с `Access is denied` — и это молча уехало в stderr. Куст остался висеть,
  держа `SOFTWARE` открытым, и следующие два часа **любой** `DISM /Image:C:\` падал с
  `Error: 32`, а в `dism.log` — `Failed trying to determine the OS Version. HRESULT=0x80070020`.
  Диагноз занял три захода (Cleanup-Mountpoints, Cleanup-Wim, чтение лога).
  **Что сделать:** обёртка для offline-реестра, которая (а) проверяет код возврата `reg unload`
  и орёт, если не выгрузился; (б) перед DISM-операциями проверяет `reg query HKLM` на чужие
  кусты и снимает их. Плюс правило: после любого `reg load` в скрипте — обязательная проверка
  выгрузки, а не `| Out-Null`.
- **`shutdown.exe` в WinPE отсутствует** — перезагрузить клиента можно только `wpeutil reboot`
  (поймано на 160450: `shutdown /r /t 15` вернул `CommandNotFoundException`, машина не ушла в
  ребут). Отложенный ребут — `Start-Process cmd -ArgumentList '/c timeout /t 20 & wpeutil reboot'`,
  иначе агент умирает раньше, чем отдаёт ответ. Просится команда `szcli reboot <СЗ>`, которая
  сама выбирает способ по среде (PE → `wpeutil`, обычная винда → `shutdown`).
- **Scratch space: `DISM /Cleanup-Image` требует ≥1024 МБ**, на 512 предупреждает
  «may cause unexpected behavior». Дефолт `build-winpe.ps1` поднят до 1024.
- **Кириллица в `.cmd` для PE не работает вообще** (поймано на первой же сборке 2026-07-29):
  консоль WinPE — cp437 с растровым шрифтом, русский текст выводится как `?????` в любой
  кодировке файла. Поэтому текст в `startnet.cmd`/`szdiag.cmd` — **латиница**, вопреки общей
  конвенции проекта на русский вывод. В самом агенте (.NET, UTF-8) русский остаётся.

**✅ E2E ПРОЙДЕН (2026-07-29, СЗ 160450, MSI MS-7E81 / Ryzen 5 7500F).** Загрузились с флешки →
агент сам вышел online (`192.168.94.114`, hostname `MININT-UD2BM8G`) → `szcli exec` и
`szcli diag run` отработали. Факты:
- **Драйверы NIC не понадобились** — сетевуха на MSI B650 поднялась стоковым PE, `-DriverPath`
  не задавали. Инжект нужен только если карта не определилась.
- **.NET 8 self-contained стартует**, PowerShell в PE — `5.1.26100.1`, WMI живой.
- PE ест ~1.5 ГБ RAM (из 31.6 ГБ свободно 30.1).
- **Работают секции diag:** `system` (модель/BIOS/TPM), `cpu`, `memory` (включая
  `ConfiguredClockSpeed` — то есть детект EXPO работает), `storage` (**SMART отдаётся**: темпа,
  wear, health), `drivers`.
- **Не работают:** `gpu` — пусто (в PE нет видеодрайвера, `Win32_VideoController` молчит);
  `PowerOnHours`/`ReadErrors` в SMART пустые; `Get-NetIPAddress` вообще отсутствует (модуль
  `NetTCPIP` не входит в WinPE — в PE-скриптах использовать `ipconfig`/WMI).
- **Диск клиента виден** (`C:` 930 ГБ NTFS, свободно 244) — offline-разбор возможен.

**Осталось по направлению:**
1. **Кодировка вывода `exec` в PE ломает кириллицу** (см. п. 17) — вылезло сразу.
2. **Offline-разбор винды клиента из PE** — главная ценность, ещё не сделана: секции
   `events`/`reboots`/`whea`/`reliability` сейчас читают журнал **самого PE** (пустой), а надо
   `C:\Windows\System32\winevt\Logs\*.evtx` клиента через `Get-WinEvent -Path`. Нужен
   PE-вариант этих проб с автопоиском диска с виндой. Тогда «машина не грузится» закрывается
   целиком: журналы + минидампы + реестр.

### 17. `exec`/RunDiag: принудительный UTF-8 для дочернего PowerShell

**Подтверждено на обычном клиенте (2026-07-31, СЗ 111111).** Опасение сбылось: в `diag.md`

### 18. Секция `whea`: отдавать MCA-детали, а не только текст сообщения

**Боль (2026-07-29, СЗ 160327 — Ryzen 5 5600 / A520M-A II, спонтанные вырубоны).** Секция `whea`
в `diag.md` выдала только локализованный текст события («Произошла неисправимая аппаратная
ошибка… Machine Check Exception… Bus/Interconnect Error»), причём в битой кодировке (см. п. 17).
Всё, что реально нужно для диагноза, лежит в `EventData` XML и в отчёт **не попадает**: пришлось
отдельным `szcli exec` тянуть `([xml]$_.ToXml()).Event.EventData.Data` — оттуда `MCABank=27`,
`MciStat=0xfaa000000000080b`, `MciMisc=0xd0130fff00000000`, `ErrorType=10`, `MemorIO=2`,
`MemHierarchyLvl=3`, `Participation=0`. Один лишний заход на каждый кейс с MCE.

**Что сделать.** В секции `whea` для событий `Id=17/18/19/20/47` печатать поля `EventData`
(`MCABank`, `MciStat`, `MciAddr`, `MciMisc`, `ErrorType`, `TransactionType`, `Participation`,
`RequestType`, `MemorIO`, `MemHierarchyLvl`, `Timeout`, `ApicId`) и рядом — расшифровку:
* `ErrorType`: 8=Cache, 9=TLB, 10=Bus/Interconnect, 11=Memory (по WHEA `MCA_EXCEPTION`);
* биты `MciStat`: 63 VAL, 62 OVER, 61 UC, 60 EN, 59 MISCV, 58 ADDRV, 57 PCC — «UC+PCC = фатальная,
  контекст ядра испорчен», «OVER = ошибок было больше, чем банк успел записать»;
* младшие 16 бит `MciStat` = MCA error code (для Bus/Interconnect формат `0000 1PPT RRRR IILL`).

**Критерий готовности.** На кейсе вида 160327 `diag.md` без единого `exec` отвечает: банк, тип
ошибки словами, флаги VAL/OVER/UC/PCC и код ошибки — то есть достаточно, чтобы отличить
«память/IF» от «PCIe/кэш».

### 19. `lhmmon` намертво виснет, если OCCT уже держит сенсоры

**Боль (2026-07-29, СЗ 160327).** Схема «lhmmon пишет CSV 1/с + OCCT грузит железо» **не
работает**, когда оба стартуют вместе: lhmmon записал **ровно один сэмпл** (файл 8822 байт,
`LastWriteTime` = момент старта) и застыл — процесс жив, `Responding=True`, но `cpuSec=0.1`
и CSV не растёт. Перезапуск lhmmon **поверх уже работающего** OCCT дал ровно то же самое
(«STILL FROZEN»). Причина — оба лезут к одному кольцевому драйверу мониторинга (WinRing0/SVI2),
и OCCT держит его эксклюзивно.

Цена ошибки высокая: прогон, который **воспроизвёл дефект на 11-й минуте**, остался без
температуры и напряжений CPU в момент обрыва — а это ровно те данные, ради которых логгер и
поднимали. Пришлось на ходу заменять на GPU-логгер поверх `nvidia-smi` (NVML с OCCT не конфликтует).

**Что сделать.** Не полагаться на LHM во время OCCT:
- либо снимать сенсоры **самим OCCT** (у него есть CSV-мониторинг) и забирать его файл — но
  проверить, что он флашится на диск, а не только в конце теста (при вырубоне «в конце» не бывает);
- либо разделить прогоны: сенсорный лог отдельно от OCCT (напр. FurMark/Prime под LHM);
- либо логгер на источниках, которые не воюют за драйвер: `nvidia-smi` (GPU), perf counters (CPU load).
  CPU temp/vcore так не снять — это и есть дыра, которую надо закрыть.
- В `szcli` просится команда `sensors <СЗ>` (есть в бэклоге) — она обязана **проверять, что лог
  реально растёт**, а не только «процесс запустился». Сейчас факт зависания ловится глазами.

**Критерий готовности.** Стресс-прогон отдаёт непрерывный ряд CPU temp/vcore/power вплоть до
секунды вырубона; при конфликте инструментов команда сообщает об этом сразу, а не молча пишет
один сэмпл.

### 20. `nvidia-smi -f <файл>` буферизует — для лога вырубона непригоден

**Боль (2026-07-29, СЗ 160327).** `nvidia-smi --query-gpu=… --format=csv -l 1 -f gpu.csv`,
запущенный detached, оставил файл **0 байт** спустя 15 секунд: вывод буферизуется и до диска

который на каждой итерации вызывает `nvidia-smi --format=csv,noheader,nounits` и дописывает

**Что сделать.** Когда будет команда `szcli sensors`, GPU-ветку писать именно циклом с дозаписью,
а не `-l/-f` самого nvidia-smi. Заодно фиксировать `clocks_event_reasons.active` (throttle-маска:
`0x4` = SW Power Cap) — сразу видно, упёрлась ли карта в лимит мощности.

**Критерий готовности.** После жёсткого вырубона в CSV есть строки вплоть до последней секунды.

### 21. `diag` не видит TDR: секция событий берёт только Critical/Error

**Боль (2026-07-30, СЗ 160521).** Заявка «в игре через 5-10 минут вылетает ошибка драйвера».
`diag.md` по всем секциям дал **чистый лист**: WHEA пусто, BSOD ноль, минидампов нет, ребутов нет,
SMART в норме. По отчёту машина здорова — и это ложный вывод, потому что **TDR в секцию событий
не попадает вообще**:
- `Display` / `amdkmdag` события 4101 — уровень **Warning**, а секция `events` фильтрует
  Critical+Error;

### 25. Долгий `exec` под 100% нагрузкой вешает exec-канал агента наглухо

**Боль (2026-07-30, СЗ 160450).** Гоняли OCCT (Combined Extreme AVX-512 + Memory) на клиенте и
запустили мониторинг **одним длинным `exec`** со `Start-Sleep`-ожиданием конца теста (~9 мин).
Под 100% CPU агент **перестал отвечать на exec совсем**: `szcli exec` трижды подряд вернул

длинный exec держит единственный воркер, и очередь новых exec встаёт намертво.

- Мониторинг долгих тестов НЕ держать длинным `exec` со сном: запускать нагрузку **detached**

  перезапускать его, а не требовать ручного рестарта всего агента.
- `szcli` при таймауте exec должен слать агенту **cancel**, чтобы на клиенте не оставался
  крутиться осиротевший скрипт (сейчас клиент szcli отваливается по своему `--timeout`, а скрипт
  на агенте продолжает выполняться и держит слот).

**Критерий готовности.** Во время OCCT/стресса на клиенте `szcli exec <СЗ> "<короткий скрипт>"`
отвечает штатно; таймаут одного долгого exec не убивает канал; агент не требует ручного рестарта.

### 26. Организовать логику восстановления/перевстановлення Windows (workflow, а не россыпь скриптов)

**Боль (2026-07-30, СЗ 160450).** Полный цикл «незагружающаяся винда → диагноз → перевстановлення
без формата → перенос данных → починка доступа → верификация» прошёл **десятками ad-hoc

  файлов — каждый пункт отдельный скрипт;
- **форс-бут** руками: снять авто-repair (`recoveryenabled No`, `bootstatuspolicy IgnoreAllFailures`),
  `reg load SYSTEM` → `CrashControl\AutoReboot=0` (+ обязательный контроль `reg unload`);
- **сборка установочной флешки** руками: `diskpart clean/format fat32`, `robocopy` с ISO без

  залоченные → обход через .NET `Set-Acl` (см. п. про ACL и память `acl-after-reinstall-windows-old`);
- по пути дважды влетел в свои же грабли: секция диага называется `storage`, а не `disks` (CLI молча

**Что сделать.** Собрать восстановление в набор команд `szcli` (или подкоманды `szcli win …`), чтобы
типовые шаги были одной командой с проверками, а не ручным скриптом:
- `szcli win bootdiag <СЗ>` — единый отчёт по незагружающейся ОС: SrtTrail, BCD (с авто-монтированием
  ESP), offline-события последней загрузки, minidumps (с hex+именем bugcheck — см. п.13), UBR-vs-файлы,
  вердикт «загрузчик/ОС/железо»;
- `szcli win forceboot <СЗ> [--revert]` — снять/вернуть авто-repair + auto-reboot одной командой,

- `szcli win mkinstaller <СЗ> --iso <path> --usb <disk>` — собрать загрузочную флешку с защитой от
  выбора не того диска (BusType/размер), авто-Split при install.wim >4 ГБ;
- `szcli win migrate <СЗ>` — перенос данных из `Windows.old` в новый профиль: разведка + Move в пределах
  тома + отчёт по крупному/аномальному AppData + предупреждение про DPAPI-пароли/sync;

**Критерий готовности.** Следующая незагружающаяся заявка проходит цикл на командах `szcli win …` без

### 27. Секция `storage` не даёт связку «pagefile → физический диск» и прячет uncorrectable

**Боль (2026-07-31, СЗ 111111, редкие BSOD 0x154/0x1A).** Диагноз — умирающий SATA HDD, на котором
лежит **единственный pagefile**: Memory Compression читает страницу из pagefile → диск отдаёт
`STATUS_DEVICE_DATA_ERROR (0xC000009C)` → `0x154_c0000006_c000009c_nt!RtlDecompressBufferLz4`.
Секция `storage` эту картину **не собирает**, пришлось писать отдельный `exec`-скрипт:

- **где pagefile — не показано вообще.** Без `Win32_PageFileUsage` связь «битый диск ↔ BSOD» не
  выводится. Оказалось `D:\pagefile.sys`, 19 ГБ, на диске 0 (Toshiba 33363 ч).
- **нет маппинга раздел → физический диск.** В отчёте буквы (C 251, D 931, E 680, F 466) и отдельно
  физдиски — какая буква на каком диске, надо угадывать по размерам. Здесь C+E = один NVMe, а

- **`ReadErrors` печатается без различения corrected/uncorrected.** В `diag.md` было `ReadErrors:
  393` — выглядит как «raw read error rate, у Toshiba это норма». На деле

- **`HealthStatus: Healthy` у диска с 393 uncorrectable и 57 событиями bad block** — активно
  вводит в заблуждение. Нужен свой вердикт, а не перепечатка Windows-статуса.
- **дисковые события не входят ни в одну секцию.** `disk` ID 7 («на устройстве плохой блок») —

- в `storage`: печатать `Win32_PageFileUsage` + явную строку «pagefile на диске N (<модель>, <шина>)»;

- в `events` (или отдельной подсекцией `storage`): `disk` 7/11/51/153, `Ntfs`, `volmgr` — с

- подсказку в духе существующих: «pagefile на диске с uncorrectable read errors → 0x154/0x1A
  UNEXPECTED_STORE_EXCEPTION / MEMORY_MANAGEMENT, лечится переносом pagefile + заменой диска».

**Критерий готовности.** Один прогон `szcli diag run <СЗ> storage` даёт ответ на вопрос «на каком
физическом диске лежит pagefile и здоров ли он» без единого ad-hoc `exec`.

### 28. `szcli exec "<строка>"` — хостовый PowerShell съедает `$`-переменные

**Боль (2026-07-31, СЗ 160636, offline-диагностика из WinPE).** Три захода подряд угроблены на то,
что скрипт в двойных кавычках **разворачивается хостовым PowerShell до отправки агенту**:

- `$p='...\SrtTrail.txt'; if (Test-Path $p)` приехал на агента как `='...\SrtTrail.txt'; if (Test-Path )`
  → `CommandNotFoundException` + `MissingMandatoryParameter`;
- `@{n='Msg';e={($_.Message -replace ...)}}` приехал как `@{n='Msg';e={(.Message -replace ...)}}`
  → каскад `Missing expression after ','` / `The hash literal was incomplete` / `Try statement is
  missing its Catch`.

Диагноз в обоих случаях **не читается**: возвращается сырой CLIXML (`#< CLIXML <Objs Version=...`)
с `_x000D__x000A_` вместо переносов — на экране каша, в которой сам факт «переменная пропала» виден
только если вглядываться в `+ ... ~~~~` маркеры. Обход — всегда `exec -f <файл>`, но об этом
вспоминаешь уже после третьего провала.

**Что сделать.**
- в `szcli exec` при inline-строке **предупреждать**, если в аргументе есть `$` — «строка обработана
  твоим шеллом; для скриптов с переменными используй `-f`»; либо просить одинарные кавычки;
- **распаковывать CLIXML на стороне CLI** — stderr агента приводить к человеческому виду
  (`Deserialize` или хотя бы замена `_x000D__x000A_` → перенос и вырезание XML-обвязки), чтобы
  ошибка PowerShell читалась как ошибка, а не как дамп;
- в `--help` к `exec` — строчка про `-f` как способ по умолчанию для всего сложнее одной команды.

**Критерий готовности.** Скрипт с `$`-переменными, отправленный inline, либо отрабатывает верно,
либо даёт одну внятную строку «используй -f»; ошибка PowerShell на агенте приходит читаемым текстом
без CLIXML-обвязки.

### 29. Вывод `szcli exec` рвёт кириллицу — свои же заголовки приходят как `????`

**Боль (2026-07-31, СЗ 160636).** Каждый `Write-Output '=== Драйверы, изменённые 14-17 июля ==='`
вернулся как `=== ????????, ?????????? 14-17 ???? ===`. Латиница и цифры целы, кириллица —

Значит чинится **на стороне агента**, одной строкой в обёртке запуска — правку CLI можно не ждать.

**Критерий готовности.** `szcli exec 160636 "Write-Output 'Проверка кириллицы: ёжик'"` возвращает

### 30. Засев агента из WinPE: после починки винда сама возвращается online под своей СЗ

**Боль (2026-07-31, СЗ 160636).** Цикл «чиню из WinPE → ребут → винда поднялась» **рвёт связь**:
в WinPE агент был онлайн и всё делалось одной командой, а на восстановленной системе агента нет.
Чтобы доделать работу (заблокировать сорвавшийся KB, прогнать `DISM /RestoreHealth`, снять
временные правки `AutoReboot`/`bootstatuspolicy`), надо **физически идти к машине**: тащить
`SzDiag.Updater.exe` с шары, запускать от админа, руками вбивать номер СЗ. Причём именно в этот
момент машина интересна больше всего — первый старт после лечения.

**Что уже есть (не изобретать заново):**
- `agent.exe --resume <statePath>` (`Program.cs:64`) — полностью headless: берёт СЗ из `state.json`,
  сам ищет hub (`HubDiscovery`), поднимает доступ, регистрируется. Bounded-ретрай 10×30с — переживает
  медленный подъём сети после загрузки;
- автостарт-задача под SYSTEM — `WindowsSystemAccessManager.cs:108` (`-AtStartup` → `--resume`);
- `WinPeAccessManager` — в PE открывать/откатывать нечего, связь идёт исходящим SignalR.

**Чего не хватает.**
1. **Офлайн-искра.** Автостарт ставится `Register-ScheduledTask` — только по живой системе. Из PE
   в образ на `C:` задачу не воткнуть (TaskCache с бинарными триггерами и хешами руками — хрупко).
   Ставить правкой офлайн-куста **службу** (`HKLM\SYSTEM\ControlSet001\Services\<name>`, `Start=2`):
   стартует под SYSTEM **до логина**, UAC не мешает, пароль юзера не нужен. Одноразовая —
   при первом старте агент регистрирует свой штатный `szdiag-autostart-<СЗ>` и сносит искру.
   (`RunOnce` не годится: контекст вошедшего юзера + манифест `requireAdministrator` = UAC-промпт,
   а если юзер не админ — вообще мимо.)
2. **Режим «принять СЗ» вместо `--resume`.** `ResumeAsync` переподнимает доступ *по флагам*
   открытого состояния; при засеве флагов нет, доступ надо открывать с нуля. Нужен `--adopt <СЗ>`
   либо `--resume` с пустым состоянием → полный `Open`.

**Что сделать.** Команда `szcli winpe seed <СЗ>` (агенту в PE): копирует пакет агента на диск
клиента, пишет `state.json` с номером СЗ, ставит службу-искру в офлайн-кусте, отчитывается что
засеяно и куда. Обязательно — парный **`revert`**: снос службы, пакета и `state.json` (инвариант
«каждый шаг Open парен шагу Revert» — следов не остаётся).

**Критерий готовности.** После `szcli winpe seed <СЗ>` + ребута восстановленная машина **сама**
появляется в `szcli list` под тем же номером СЗ, без похода к машине и без ручного ввода номера;
`revert` не оставляет ни службы, ни файлов.

### 31. Выборка событий по `Id` + `MaxEvents` глотает редкие критичные — привела к неверному диагнозу

**Боль (2026-07-31, СЗ 160636).** Из WinPE запросил offline-журнал одним фильтром:


Вернулось 40 записей, **почти целиком забитых `Id=55`** (`Kernel-Processor-Power` пишет по 12 штук

объявил железо чистым, а причиной — сорванное обновление.

На живой системе тех же событий оказалось **27+**, с 18.03 по 16.07. Вывод пришлось разворачивать
на 180°: обновление было **жертвой** (машина вырубилась в 22:29:21 ровно посреди установки пакета,

Усугубляет то, что в WinPE время **UTC**, а на живой системе локальное: сортировка «последние N»
съезжает, и глазами расхождение не ловится.

**Что сделать.**
- в `szcli win bootdiag` (п.26) и в секции `events` — **никогда не смешивать шумные и редкие Id в
  одной выборке с общим `MaxEvents`**: запрашивать каждую группу отдельным запросом со своим
  лимитом, шумные (`55`, `98`, `10016`, `10010`) — либо исключать, либо считать агрегатом;
- **критичные Id брать без лимита за период**: `41` (Kernel-Power), `1001` (BugCheck), `6008`,
  `WHEA-Logger` — их единицы, резать их нечем;
- добавить в отчёт **счётчик по каждому Id за всё время** («Kernel-Power 41: 27 шт, последнее
  16.07 22:29») — отсутствие события должно быть явным нулём, а не молчанием;
- `LiveKernelReports` — **обязательный пункт** офлайн-осмотра наравне с `Minidump`: там лежат
  живые дампы TDR (`0x193`), которые при hard-off единственные и остаются;
- время в offline-режиме печатать с явной меткой UTC/local.

**Критерий готовности.** Отчёт `bootdiag` по этой же машине из WinPE даёт «Kernel-Power 41: 27 шт»
и «LiveKernelReports: 37 файлов» без единого доп. запроса — то есть диагноз «hard-off, а не
обновление» ставится сразу, а не после загрузки в ОС.

### 33. `szcli exec` глохнет под тяжёлой нагрузкой — критерий п.2 на практике не выполняется

**Боль (2026-07-31, СЗ 160636, длинный прогон OCCT).** Во время OCCT (`Combined`, `Mode: Extreme`,
`OcctInstructionSet: Avx512`, все ядра) агент **перестал отвечать на `exec`**:

```
Таймаут: агент СЗ 160636 не ответил на exec
```

При этом **heartbeat шёл нормально** — `szcli list` всё время показывал СЗ `online` с растущим
аптаймом (2ч 32мин). То есть агент жив и на связи, но тяжёлый запрос не обслуживает: три попытки
подряд (два фоновых мониторинга и один прямой вызов) ушли в таймаут, включая заведомо лёгкий
скрипт без разбора CSV.

Это ровно тот сценарий, ради которого `exec` и делался — в п.2 записан критерий «сбор данных
работает под полной нагрузкой, когда sshd мёртв». На живой заявке он **не выполнился**: мониторить
стресс-тест, ради которого всё затевалось, оказалось нечем, кроме `szcli list`.

Вероятная причина: OCCT в `Extreme` занимает все ядра, а агент (.NET, обычный приоритет) не
получает достаточно квантов, чтобы поднять дочерний `powershell.exe`, дождаться его и вернуть
ответ в отведённое окно. Лёгкий периодический heartbeat проскакивает, тяжёлый синхронный
запрос — нет.

**Что сделать.**
- поднять **приоритет процесса агента** (`ProcessPriorityClass.AboveNormal`/`High`) — он служебный
  и обязан отвечать именно тогда, когда машине плохо; при желании только на время exec;
- дочернему `powershell.exe` задавать приоритет не ниже обычного и **не наследовать** прижатый;
- ввести **асинхронный режим**: `szcli exec --async` → агент кладёт результат в файл и отдаёт
  `RequestId`, CLI забирает готовое отдельным вызовом. Тогда таймаут перестаёт зависеть от того,
  успел ли скрипт отработать под нагрузкой;
- вынести «дежурную телеметрию» (аптайм, признаки дефекта, хвост лога теста) в **лёгкий ответ на
  heartbeat**, а не в полноценный exec — во время стресс-теста нужны именно эти несколько строк;
- в CLI при таймауте писать не голое «не ответил», а подсказку «агент на связи (heartbeat N сек

**Критерий готовности.** После `szcli freeze` Windows Update не может стартовать установку в

пережившая ребут, и есть рабочая); незакрытая заморозка видна в `list` и не даёт закрыть СЗ без
предупреждения.

### 39. `szcli exec` работает под админом — часть системных операций упирается в Access denied

### 35. Незавершённая CBS-транзакция = мина при выключении; нет ни оценки времени, ни стоп-крана

**Боль (2026-07-31, СЗ 160636).** Отправили машину в ребут применять `pending.xml` **46,5 МБ**.
Через 16 минут — всё та же крутилка, а сервис закрывался (рубильник). Решение принимали вслепую:
**никто не мог сказать, это нормальная длительность или зависание.**

Прикидка постфактум: 46,5 МБ `pending.xml` — это не объём данных, а **список операций** (обычная
транзакция 1–5 МБ), то есть сотни тысяч файловых и реестровых операций. На **NV3 без DRAM** —
худший случай для мелких синхронных записей — это реально 40–60 минут. Крутилка, вероятнее всего,
была **рабочей**, но машину обесточили на 18-й минуте. Ровно тем же способом (вырубон посреди
применения пакета) эта система умерла 16 июля.

Единственный доступный признак «живо или встало» — **мигание индикатора диска на корпусе**, то
есть человек рядом. Программно из hub мы про машину в этот момент не знаем ничего: агента ещё нет,
сеть не поднята.

**Что сделать.**
- **перед** ребутом: `szcli` считает размер `pending.xml` + число `PendingFileRenameOperations`
  + тип накопителя (DRAM-less?) → печатает **оценку времени** и явное предупреждение
  «не выключать N минут»;
- **стоп-кран**: если на СЗ висит незавершённая транзакция, `szcli close` и любая команда
  выключения требуют подтверждения с текстом про риск кирпича;
- **признак прогресса без агента**: в `bootdiag` (п.26) добавить чтение `poqexec.log` и
  `CBS.log` из WinPE **после** неудачной загрузки — по ним видно, докуда дошло применение и
  оборвалось ли оно;
- в док по эксплуатации — правило: **не начинать применение крупной транзакции меньше чем за час
  до обесточивания сервиса**.

**Найден дискриминатор «крутилка рабочая vs мёртвая» (2026-08-04, та же 160636).** Вопрос
«она работает или встала?» решается **из WinPE за одну команду, без человека у корпуса**: сравнить
`LastWriteTime` ключевых файлов офлайн-системы с моментом последнего shutdown. Работающий POQ
непрерывно пишет — если после 15+ минут крутилки **ни один** файл не сдвинулся, применение мёртвое.

Факты по 160636: после 15+ мин крутилки 04.08 всё имело метку **31.07 19:42:38-40** —
`bootstat.dat`, `System.evtx`, `Setup.evtx`, кусты `SYSTEM`/`SOFTWARE`, `CBS.log`, `poqexec.log`.
Ноль записей за 4 дня и за сегодняшнюю попытку → система не доходит даже до старта EventLog,
ждать бессмысленно. Дополняющие признаки той же картины: `pending.xml` жив (48,7 МБ),
`PackagesPending` полон, `poqexec.log` **без завершённого блока** для текущей транзакции
(последний `EndTime` — от прошлой), при этом `UBR` **уже перещёлкнут** на новый (26200.**8973**
против .8737 после отката) — билд пишется оптимистично, до завершения POQ, так что «UBR новый»
≠ «обновление применилось».

Набор для `bootdiag`: mtime `bootstat.dat`/кустов/`*.evtx` vs время последнего shutdown из
`System.evtx` (6006) + размер `pending.xml` + наличие `PackagesPending`/`RebootInProgress` +
последний `EndTime` в `poqexec.log` + текущий `UBR`. Вывод одной строкой: «транзакция мертва
N дней, прогресса нет» либо «идёт, последняя запись M минут назад».

Мелочь оттуда же: в **PS 5.1 нет строкового range** — `'C'..'M'` для перебора букв дисков молча
даёт пусто, и скрипт «не находит том с виндой» на машине, где `C:` на месте. В PE-скриптах
перечислять буквы списком.

**Критерий готовности.** Перед ребутом с pending видно ожидаемое время и предупреждение; после
обрыва `bootdiag` из WinPE отвечает «транзакция оборвана на шаге X», а не оставляет гадать.

### 36. Тепловой отказ (THERMTRIP) неотличим от любого другого hard-off — нет методики

**Боль (2026-07-31, СЗ 160636).** Версию мастера «машина задыхается в тесной нише» проверить

падала после 1–15 часов в закрытом объёме.

`Microsoft-Windows-Time-Service` — то есть **чужие события с тем же Id**, и записал «тротлинга
нет». Смежно с п.31, но там про лимит выборки, а здесь про обязательный `ProviderName`.

- секция диага **«тепловой профиль»**: `Kernel-Processor-Power` **Id 37/86** (с явным

- **методика прогона**: тепловой сценарий проверять **в собранном корпусе**, а не на открытом
  стенде, и логировать температуру входящего воздуха (датчик платы `Temperature #1`) — на стенде
  она была 30–54 °C, у клиента будет заметно выше;
- в опросник по заявке — пункт **«где стоит системник»** (ниша, шкаф, вплотную к стене, батарея).
  Это половина диагноза при hard-off без следов, а спрашивается бесплатно.

**Критерий готовности.** По заявке с hard-off отчёт отвечает, упиралась ли машина в тепловой
лимит (события тротлинга + профиль по времени суток), и явно предупреждает, что отсутствие
WHEA/дампов теплового сценария **не исключает**.

следа — если не смотреть на сенсоры, выглядит как «тест идёт».

Причина в третьей строке его же вывода: **`Use Q to exit`** — CLI читает клавиши, и при
перенаправлённых потоках сразу получает EOF и завершается. Ровно та же природа, что у ConPTY-граблей
из CLAUDE.md: инструмент требует **живой консоли**, а не пайпа.

**Рабочий запуск (проверен, тест поехал — CPU 100 %, GPU 100 % / 170 Вт):**

```powershell
$cmd = 'start "OCCT <СЗ>" /min cmd /c ""<путь>\OCCTCmd.exe" test --schedule="<путь>" --auto-start"'
Start-Process cmd -ArgumentList '/c', $cmd -WindowStyle Hidden
```

Своё окно = своя консоль = живой stdin. Прогресс тогда читается **не из stdout, а из сенсоров**
(`sensors.csv`) — что и правильнее: проверка «тест реально грузит железо» должна идти по приборам.

**Что сделать.**
- В рецепт стресс-прогона (и в будущую `szcli stress run`): запускать OCCT **только** через `start`
  в отдельном окне, никогда с `-RedirectStandardOutput`;
- **обязательная проверка через 60 с после старта**: `CPU Total` и `GPU Core Load` из свежей строки
  CSV. Если < 90 % — тест не идёт, сообщить и не делать вид, что прогон стартовал (сегодня без этой
  проверки мы бы «гоняли» 6 часов пустоты);
- то же правило проверить для FurMark/TM5 — у них может быть та же логика ожидания клавиши.

**Критерий готовности.** `szcli stress run <СЗ> --hours N` поднимает тест, через минуту сам
подтверждает нагрузку по сенсорам и печатает ожидаемое время финиша.

### 42. Под нагрузкой машина глохнет по сети целиком — «offline» ≠ вырубон, и я на этом попался

**Боль (2026-08-04, СЗ 160636).** Через 19м46с после старта стресс-прогона СЗ ушла в offline,
ICMP не отвечал **четыре пинга подряд** с интервалом 2 с. Я объявил дефект воспроизведённым —
и **ошибся**: машина всё это время работала, тест считал, окно OCCT жило. Мастер сидел рядом и
видел корпус, я — только отвал связи.

Что важно и ново: пропал **не только heartbeat, но и ICMP**. То есть под этим профилем нагрузки
(OCCT `PowerSupply`, `LoadType: Variable`, все потоки) сетевой стек перестаёт отвечать целиком.
Раньше это списывалось на «sshd задушен» (CLAUDE.md: под OCCT sshd то глух, то отвечает) — на самом
деле глохнет **вся сетевая ответность машины**, а не конкретная служба. Значит «нет пинга» под
нагрузкой не значит вообще ничего, и `szcli exec` в этот момент тоже может не дойти.

**Дискриминатор уже лежит готовый и не используется:** в `/api/sessions` **есть поле `bootTime`**
(в этой же выдаче: `"bootTime":"2026-08-04T13:03:16.5+03:00"`). Реальный вырубон отличается от лага
однозначно — **сменой `bootTime`** после возврата. Направление из CLAUDE.md («heartbeat несёт
LastBootUpTime») по факту наполовину реализовано; осталось на этом построить логику.

**Что сделать.**
- `szcli watch`/`list`: различать **`offline (лаг?)`** — heartbeat опоздал, но `bootTime` тот же и
  СЗ вернулась — и **`ВЫРУБОН`** — вернулась с новым `bootTime`. Второе печатать красным и писать
  в таймлайн СЗ «продержалась N минут под тестом»;
- любой автоматический вывод о вырубоне — **только по смене `bootTime`** либо по offline дольше
  порога (10+ мин), никогда по одному отвалу heartbeat и никогда по ICMP;
- в рецепт стресс-прогона: перед стартом записать `bootTime`, после — сравнить. Это и есть
  измерение «времени до отказа», сейчас оно делается глазами;
- честно зафиксировать в методике: **под нагрузкой отсутствие сети — норма, а не симптом.**

**Критерий готовности.** Во время стресс-прогона `szcli` не сообщает о вырубоне, пока `bootTime`
не сменился; после реального отказа сам печатает время, которое машина продержалась.
