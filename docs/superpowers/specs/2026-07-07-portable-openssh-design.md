# Портативный OpenSSH для агента sz-diag

**Дата:** 2026-07-07
**Статус:** дизайн одобрен, ждёт ревью спеки

## Проблема

Агент `SzDiag.Agent` на клиентских машинах почти на каждой второй машине не может
открыть SSH-доступ. Три отдельных симптома, один общий корень — зависимость от
**системного** Windows OpenSSH, который на клиентских машинах в непредсказуемом
состоянии.

1. **Виснет на «Открываю доступ»** — если службы `sshd` нет,
   `WindowsSystemAccessManager.Open` вызывает
   `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0` (DISM/Windows
   Update). Windows Update на клиентской машине часто недоступен (корпоративная
   политика, отключённая служба `wuauserv`, отвал серверов обновлений) даже при
   живом интернете. Итог — 2 минуты таймаут и `OpenSshUnavailableException`.
   **Интернет ≠ доступный Windows Update.**

2. **Падает на `Start-Service sshd`** — служба есть, но host-ключи побиты жёстким
   выключением питания (`sshd -T` → `Unable to load host key ... invalid format`,
   `no hostkeys available -- exiting`), либо SID-корапция
   (`get_passwd: lookup_sid() failed: 1332`). Наблюдалось на реальной машине
   (СЗ 159289) после нескольких аварийных отключений питания. Пользователь видит
   голый дамп PowerShell без диагностики.

3. **Зависимость от чужого состояния** — даже когда всё работает, мы завязаны на
   здоровье системного OpenSSH: чужой `sshd_config`, чужие ключи, чужой жизненный
   цикл службы.

## Цель

Агент перестаёт зависеть от системного OpenSSH. Открытие доступа должно работать
одинаково на: чистой машине (sshd нет вообще), машине с рабочим системным sshd,
машине с битым системным sshd — без Windows Update и без ручного вмешательства.

## Решение: портативный sshd дочерним процессом

Агент носит с собой портативный Win32-OpenSSH и поднимает `sshd.exe` как **дочерний
процесс** со своим конфигом и свежими host-ключами. Системный OpenSSH не трогается
(кроме временной остановки, если он занимает порт — см. ниже).

### Почему именно так

- **Нет Windows Update** — бинарники уже на машине, ставить нечего. Симптом #1
  исчезает как явление (`OpenSshUnavailableException` удаляется).
- **Свои host-ключи каждую сессию** — генерируются заново при каждом открытии
  доступа во временную папку. Битый host-ключ физически невозможен. Симптом #2
  исчезает.
- **Fail-closed** — sshd дочерний процесс агента, умирает вместе с ним. Краш агента =
  доступ немедленно закрыт. Совпадает с моделью угроз: клиентская машина
  недоверенная, лишний живой sshd после падения агента — это дыра, а не удобство.
- **Ноль зависимости от чужого состояния** — свой sshd, свой конфиг, свои ключи.

## Компоненты

### 1. Портативные бинарники OpenSSH — `dist\client\ssh\`

- `sshd.exe`, `ssh-keygen.exe`, `sftp-server.exe` + нужные dll (libcrypto и пр.).
- Источник: релиз `github.com/PowerShell/Win32-OpenSSH` (OpenSSH-Win64.zip).
- **`build-dist.ps1`** один раз качает релиз, кэширует распакованным в
  `client-tools\ssh\` (в `.gitignore`, как OCCT/TM5), при сборке копирует в
  `dist\client\ssh\`. В git бинарники не коммитятся. Нужен интернет на **хосте** при
  первой сборке; на клиентах интернет уже не нужен.
- Если `client-tools\ssh\` уже есть — скрипт не качает повторно (идемпотентность,
  как с прочими стресс-утилитами).

### 2. `PortableSshServer` (новый класс в `SzDiag.Agent`)

Единственная ответственность — жизненный цикл дочернего `sshd.exe`.

- **`Start(port, authorizedKeysPath)`**:
  - генерирует свежие host-ключи в `ProgramData\szdiag\ssh\` через
    `ssh-keygen -A` (или явно ed25519/rsa) — старые, если были, перезаписываются;
  - пишет собственный `sshd_config` в ту же папку: свой `HostKey`, `Port`,
    `AuthorizedKeysFile` на нашу папку, `LogLevel VERBOSE`,
    `Match Group administrators` с нашим `AuthorizedKeysFile` (иначе Windows OpenSSH
    для админов форсит `administrators_authorized_keys`);
  - запускает `sshd.exe -f <config> -D -E <log>` дочерним процессом;
  - проверяет, что процесс жив через ~1–2 сек и порт слушается; если sshd умер —
    читает `<log>` и бросает исключение с последними строками лога.
- **`Stop()`** — kill процесса (идемпотентно; повторный вызов безопасен).
- Юнит-тестируется: генерация `sshd_config` (пути/порт/AuthorizedKeysFile), разбор
  лога при неудачном старте, идемпотентность `Stop`. Реальный запуск `sshd.exe` — в
  ручном e2e.

### 3. `WindowsSystemAccessManager` — упрощение `Open`/`Revert`

**Удаляется:**
- шаг 1 (Add-WindowsCapability / Windows Update);
- шаг 2 (`Set-Service sshd`; `Start-Service sshd`);
- `OpenSshUnavailableException`;
- флаги `InstalledOpenSsh`, `StartedSshService` из `RevertState`.

**Добавляется:**
- шаг «если системный sshd в состоянии Running — остановить на время сессии»
  (`Stop-Service sshd`), флаг `StoppedSystemSshd`;
- шаг `PortableSshServer.Start(...)`, флаг `GeneratedHostKeys`;
- `administrators_authorized_keys` заменяется на наш `AuthorizedKeysFile` в папке
  `ProgramData\szdiag\ssh\` (конфиг sshd указывает на него) — меньше возни с ACL
  системного файла. *(Уточнить при реализации: если Match-override не сработает на
  конкретной сборке OpenSSH, оставить путь через `administrators_authorized_keys`.)*

**Новый порядок `Revert`** (обратный, идемпотентный, каждый шаг под флагом):
1. kill дочернего sshd (`PortableSshServer.Stop`);
2. удалить host-ключи и sshd_config (`ProgramData\szdiag\ssh`), флаг
   `GeneratedHostKeys`;
3. firewall-правило;
4. `LocalAccountTokenFilterPolicy`;
5. учётка `svc-diag`;
6. `authorized_keys`;
7. **вернуть системный sshd** (`Start-Service sshd`), если гасили, флаг
   `StoppedSystemSshd`;
8. снять watchdog scheduled task.

### 4. Watchdog — переживание reboot/краша

Роль сохраняется и расширяется. Дочерний sshd умирает с агентом (доступ закрыт), но
следы в ОС остаются: firewall-правило, `svc-diag`, token policy, authorized_keys,
остановленный системный sshd, host-ключи в `ProgramData`. Их чистит watchdog
(scheduled task под SYSTEM) — единственный, кто уберёт следы после reboot, потому что
сам агент туда уже не вернётся. `--revert` использует тот же обновлённый `Revert`,
включая возврат системного sshd и удаление наших ключей.

## Диагностика и внятные ошибки

- `PortableSshServer.Start` при неудаче показывает последние строки лога sshd с
  формулировкой «sshd не стартовал: <причина>», а не молчит и не роняет сырой дамп.
- Проверка порта перед стартом: если порт 22 держит чужой (не sshd) процесс —
  сообщение «порт 22 занят процессом <имя>, освободите или укажите другой SshPort»,
  без попытки убить чужое.
- Перед каждым шагом `Open` — человекочитаемый `Announce()` («Останавливаю системный
  sshd…», «Генерирую host-ключи…», «Запускаю sshd…»), чтобы по `agent.log` было
  видно, на чём встали.

## Риск для валидации на реальной машине

Windows OpenSSH обычно запускает `sshd` под `LocalSystem`, т.к. для создания
logon-токена входящего пользователя нужен `SeTcbPrivilege`. Дочерний `sshd` под
админ-агентом может не суметь залогинить `svc-diag` («unable to create logon
token»). **Это первый пункт e2e-проверки.** Если подтвердится — фолбэк: запускать
`sshd.exe` не напрямую дочерним процессом, а транзиентной scheduled task под SYSTEM,
привязанной к жизни сессии и чистящейся тем же watchdog. Не закладываемся молча на
«должно сработать» — проверяем явно и имеем план B.

## Тестирование

- **`PortableSshServer`** — юниты: генерация `sshd_config`, разбор лога неудачного
  старта, идемпотентность `Stop`.
- **`WindowsSystemAccessManager`** — обновить тесты под новые флаги
  (`StoppedSystemSshd`, `GeneratedHostKeys`), убрать про
  `InstalledOpenSsh`/`StartedSshService`.
- **`RevertState`** — сериализация новых флагов.
- **Ручной e2e** (дополнить `docs/TESTING.md`): три сценария — чистая машина,
  рабочий системный sshd, битый системный sshd. Здесь же валидируется
  token-privilege риск.

## Что НЕ входит (YAGNI)

- Не переносим весь SSH-стек в кастомный порт/протокол — `SshPort` (по умолчанию 22)
  остаётся, hub↔CLI протокол не меняется.
- Не поддерживаем одновременную работу нашего и системного sshd — системный гасим на
  сессию.
- Не кэшируем host-ключи между сессиями — всегда свежие (устраняет корапцию).
