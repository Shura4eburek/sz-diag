# Автообнаружение hub'а по UDP-broadcast

Дата: 2026-07-03

## Задача

`AgentOptions.HubUrl` сейчас жёстко зашит в конфиге агента (`dist\client\appsettings.json`).
На многоинтерфейсной хостовой машине (несколько локальных IP) приходится вручную
угадывать, какой адрес виден клиентской машине — при пересборке/переносе на другую сеть
это ломается молча (агент падает с сырым `HttpRequestException` при старте). Дефолт
`localhost` в `build-dist.ps1` при отсутствии `-HubIp` в принципе неверен для отдельной
клиентской машины (единственный корректный случай — хост=клиент на одной машине).

Топология сети: клиент и хост **всегда в одном физическом сегменте** (одна локалка/
broadcast-домен сервисного центра) — маршрутизаторы/VPN/разные VLAN между ними не
встречаются. Это открывает путь к обнаружению через UDP-broadcast без внешней
инфраструктуры (DNS/mDNS не нужны).

## Механизм

Новый лёгкий UDP-протокол обнаружения, отдельный от TCP/SignalR-порта. Константы —
в `SzDiag.Contracts` (по аналогии с `HubRoutes`).

- **UDP-порт:** `5098` (SignalR/HTTP остаётся на TCP `5099`, не конфликтует).
- **Запрос (агент → сеть):** `SZDIAG-DISCOVER:<AgentToken>`.
- **Ответ (hub → агент):** `SZDIAG-HUB:<port>` — unicast на адрес и порт отправителя запроса.

### Hub-сторона

Новый hosted service (по образцу `OfflineSweeper`) открывает **один UDP-сокет на
`(IPAddress.Any, 5098)`** — не по сокету на интерфейс. Это осознанное упрощение
относительно первоначального замысла "сокет на каждый локальный IP": для ответа на
unicast **уже пришедшему** запросу ОС сама выбирает верный исходящий интерфейс/IP через
обычную таблицу маршрутизации (адрес отправителя — это directly-connected подсеть, для
которой всегда есть прямой маршрут через нужный NIC). Один сокет вместо N — меньше кода,
меньше сценариев отказа (не нужно перечислять/пересоздавать сокеты при смене состава
интерфейсов), а результат для клиента идентичен: ответ приходит с IP, реально видимого в
его подсети.

Обработка запроса:
- слушает входящие датаграммы на `(0.0.0.0, 5098)`;
- при получении `SZDIAG-DISCOVER:<token>` сверяет токен с `HubOptions.AgentToken`;
- при совпадении — отвечает `SZDIAG-HUB:<port>` обратно на адрес отправителя через тот же
  сокет (порт — из нового поля `HubOptions.Port`, т.к. `Urls` не всегда легко достать из
  hosted service синхронно при старте).

Если порт `5098` уже занят (например, несколько тестовых `WebApplicationFactory` хаба
поднимаются параллельно) — сервис должен тихо ничего не делать, а не ронять весь hub:
ошибка бинда UDP-сокета перехватывается и обработчик просто не запускается, HTTP/SignalR
хаба продолжают работать как обычно.

При несовпадении токена — датаграмма молча игнорируется (никакого ответа), фильтруя
случайный сетевой шум. Без крипто-подписи: по модели угроз оператора (сеть сервисного
центра, hub всегда единственный) риск подмены ограничен тем, что реальное SignalR-
подключение всё равно требует правильный `AgentToken` в заголовке — спуфер максимум
заставит агента впустую попытаться подключиться и получить 401/refused.

### Agent-сторона

Новый класс `HubDiscovery` в `SzDiag.Agent`. Если `AgentOptions.HubUrl` пуст:

1. Перебрать локальные IPv4-адреса агента (аналогично hub — исключая loopback/APIPA).
2. С каждого адреса отправить broadcast `SZDIAG-DISCOVER:<token>` на порт `5098`
   (сокет с `EnableBroadcast = true`, отправка и на широковещательный адрес интерфейса,
   и подстраховкой на `255.255.255.255`).
3. Слушать ответы на тех же отправляющих сокетах (unicast-ответ приходит на тот же
   local endpoint, откуда ушёл запрос — отдельный слушающий сокет не нужен).
4. Повторять отправку раз в ~500 мс, пока не придёт валидный ответ или не истечёт общий
   таймаут ~3 секунды (компенсация потери UDP-пакетов).
5. Первый валидный ответ `SZDIAG-HUB:<port>` → IP берётся из адреса отправителя пакета
   (`RemoteEndPoint`), порт — из тела ответа → собрать `http://<ip>:<port>`.
6. Если таймаут истёк без ответа — выбросить понятное исключение с текстом вида:
   `hub не найден в сети. Проверьте подключение к сети сервисного центра или укажите
   HubUrl вручную в appsettings.json`. Программа должна показать это сообщение читаемо
   (через существующий `Announce`/панель ошибки в `Program.cs`), а не сырой стектрейс
   `HttpRequestException`, как сейчас.

Если `HubUrl` в конфиге **не пуст** — используется как есть, автообнаружение не
запускается вообще (ручной override, старое поведение).

### Config и build-dist.ps1

- `AgentOptions.HubUrl` — дефолт меняется с `"http://localhost:5000"` на `""` (пусто =
  автообнаружение).
- `build-dist.ps1`: параметр `-HubIp` остаётся как явный override. Без `-HubIp` в
  `dist\client\appsettings.json` пишется `"HubUrl": ""` (было ошибочно `localhost`).
  С `-HubIp <адрес>` — пишется явный `http://<адрес>:<порт>` как сейчас (для
  хост=клиент на одной машине или нетипичных случаев).

## Тестирование

- **Протокол (чистые юнит-тесты, без сети):** сборка строки запроса/ответа, разбор
  входящей датаграммы, проверка токена (совпадает/не совпадает/мусор).
- **Раунд-трип через loopback:** hub-сторона и agent-сторона поднимаются на `127.0.0.1`
  с фиксированными тестовыми портами (без реального broadcast — точечная отправка на
  `127.0.0.1:<порт>`), проверяется полный цикл запрос→фильтр по токену→ответ→сборка URL.
  Тест на неверный токен — подтверждает отсутствие ответа (не throw, а timeout/null).
- Настоящий multi-NIC broadcast в разных физических сетях — ручная/полевая проверка,
  описывается в `docs/TESTING.md` как дополнение к существующему e2e-сценарию.

## Обратная совместимость

- Уже развёрнутые `appsettings.json` с явным `HubUrl` продолжают работать без изменений
  (override, автообнаружение не трогает этот путь).
- Существующие тесты `AgentOptions`/`Program.cs` не завязаны на конкретный дефолт
  `HubUrl` (проверить при реализации; если завязаны — обновить вместе с дефолтом).
