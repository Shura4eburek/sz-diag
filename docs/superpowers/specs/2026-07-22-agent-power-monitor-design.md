# Power-мониторинг агента (LibreHardwareMonitor) — дизайн

**Дата:** 2026-07-22
**Статус:** дизайн согласован, реализация не начата. **Эмпирика п.1 проведена 2026-07-23**
(LHM-логгер на живых СЗ 159873/160176) — rail +12V на массовом железе LHM НЕ читает, плюс
всплыл конфликт ring0 с OCCT; см. раздел «Находки живой обкатки» в конце.
**Контекст:** СЗ 159873 (спонтанные ребуты под нагрузкой, версия — питание/БЖ). Дефект
«плавающий», на стенде не воспроизводится за ~5ч RDR2. Нужен долгий (6ч+) стресс с
**автоматическим** сбором и анализом сенсоров, чтобы не пялиться в экран вручную и получить
цифры для решения (в т.ч. как аргумент авторизованному сервис-центру по БЖ).

## Цель

Агент во время прогона сам собирает **все** сенсоры (напряжения, температуры, частоты, load,
GPU power) и:
- **realtime** — при пробое порога сразу шлёт алерт на hub (SignalR), оператор/Claude видит
  событие с таймингом по ходу прогона;
- **пост-анализ** — копит min/max/avg по каждому сенсору, в конце пишет секцию в отчёт +
  полный CSV-лог артефактом на hub.

## Источник данных: LibreHardwareMonitorLib

Решение — **чистый LHM** (NuGet `LibreHardwareMonitorLib`), встроенный прямо в агент (.NET).
Причины: headless (весь наш доступ — по SSH, без десктопа; GUI-тулы вроде HWiNFO по SSH
падают/висят — см. docs/TESTING.md), realtime и пост-анализ тривиальны, стрим на hub через уже
существующий SignalR, без внешних процессов и лицензий.

**Покрытие (важно):** LHM на уровне HWiNFO по температурам (Zen Tctl/Tdie, GPU, диски),
частотам (CPU по ядрам, GPU core/mem), load, GPU power/voltage, VCORE/SoC (AMD SVI2/SVI3).
**Слабое место — rail-напряжения БЖ (12V/5V/3.3V):** читаются с Super I/O матери (ITE/Nuvoton),
LHM часто отдаёт без калибровки (безымянный «Voltage #N» без множителя), на свежем B850 (2025)
Super I/O может быть поддержан частично.

**Оговорка про 12V (общая для LHM и HWiNFO):** оба читают 12V с датчика **материнки**, не с
выхода БЖ. Это медленный сенсор ±5%. Микросекундный transient-спайк не видит ни один —
настоящий пруф только осциллограф на кабеле. Софт-мониторинг ловит **устойчивую** просадку;
её отсутствие не оправдывает БЖ.

**Первый шаг реализации — эмпирическая проверка:** до всего кода прогнать LHM-дамп сенсоров
на целевой матери и убедиться, что +12V читается и адекватен. Если нет — отдельным решением
добавить источник для rail (напр. HWiNFO CSV) поверх; ядро (temps/clocks/throttle/GPU) LHM
закрывает в любом случае.

## Компоненты (изоляция)

- **`ISensorSource`** — интерфейс: `SensorSnapshot Read()` (одно измерение всех сенсоров).
  Позволяет юнит-тестировать логику агрегации/порогов без железа (fake-источник).
- **`LhmSensorSource : ISensorSource, IDisposable`** — тонкий адаптер над LHM `Computer`
  (IsCpuEnabled/IsGpuEnabled/IsMotherboardEnabled/IsStorageEnabled). `Dispose()` → `Close()`,
  выгружает kernel-драйвер (WinRing0). Единственный кусок, завязанный на LHM.
- **`SensorSnapshot`** — DTO: список `(Name, Type, Value, Unit)` + метка времени.
- **`PowerMonitor`** — фоновый `Task`: в цикле каждые `SampleSeconds` (дефолт 1с) читает
  источник, обновляет агрегаты (min/max/avg по имени сенсора), сверяет с порогами; при **первом**
  пробое конкретного сенсора шлёт realtime-алерт на hub и помечает (чтобы не спамить каждую
  секунду), пишет строку в CSV. `Start()`/`StopAndSummarize()` → `PowerSummary`.
- **`MonitorThresholds`** — пороги (конфиг, дефолты ниже).
- **`PowerSummary`** — результат: агрегаты + список зафиксированных пробоев (сенсор, когда,
  значение, порог) + имя CSV-артефакта. Идёт новой секцией в `report.md`.

## Пороги (дефолты, оверрайд в конфиге)

- **12V**: вне `11.4–12.6` В (ATX ±5%).
- **Температуры**: CPU > 90 °C, GPU > 83 °C.
- **Частоты**: фиксируем min под нагрузкой; флаг, если проседает заметно ниже базовой
  (эвристика: ниже X% от max, наблюдаемого в прогоне; уточнить на живом прогоне).
- Пороги конфигурируемы (appsettings/testsuite), значения выше — дефолты.

## Realtime-канал (SignalR)

- Новый метод в `HubRoutes` (единый источник имён) + `AgentHub`: `PowerAlert(sz, text)`.
- Агент шлёт при первом пробое: напр. `«12V упал до 11.1 В (порог 11.4) в 14:32:07»`.
- Hub логирует событие (в историю СЗ) и отражает в CLI `watch` (в колонке активности/событий).
  Claude, ведя вахту, видит алерт и пингует оператора.

## Запуск (обе формы)

1. **Сквозной** — `szcli test run <СЗ>`: при включённом флаге (конфиг агента, напр.
   `Monitor.Enabled=true`) `TestRunner.Run` оборачивает весь прогон монитором — старт до шагов,
   `StopAndSummarize` после, результат отдельной секцией в отчёт. Не требует нового типа шага.
2. **`szcli power run <СЗ> <минуты> [--occt]`** — тонкая команда: «просто помониторь N часов под
   текущей нагрузкой». Опц. `--occt` дёргает OCCT-Power шаг параллельно. Это ровно кейс «OCCT
   Power 6ч» без остального тест-набора. Через `/api` (ManagementApi) → SignalR-команда агенту.

## Откат (главный инвариант)

LHM грузит ring0-драйвер (WinRing0). Штатно `LhmSensorSource.Dispose()` в `finally` выгружает.
На случай краха агента посреди прогона — флаг `MonitorDriverLoaded` в `RevertState` + парная
ветка в `WindowsSystemAccessManager.Revert` (идемпотентная выгрузка/снятие драйвера), чтобы на
клиентской машине не осталось следов. Строго по правилу «Open → парная ветка в Revert под флагом».

## Отчёт / kb

- Новая секция в `report.md` (через `ReportMarkdownBuilder`): таблица min/max/avg по ключевым
  сенсорам + список пробоев с таймингом + ссылка на CSV-артефакт.
- CSV-лог заливается на hub как артефакт (механика `Artifacts` уже есть в `TestRunOutput`).
- Технический отчёт прогона — не kb-заметка; вердикт по питанию оператор/Claude вносит в
  `діагностика.md`/`висновок.md` СЗ вручную (как сейчас).

## Тестирование

- `PowerMonitor` и пороговая логика — юнит-тесты на fake `ISensorSource` (последовательность
  снапшотов → проверяем агрегаты, момент алерта, отсутствие спама, содержимое summary/CSV).
- `LhmSensorSource` — тонкий адаптер; живой тест опционально под флагом (как `SZDIAG_LIVE` для
  vgabios) — реально читает железо стенда, по умолчанию skip.
- CSV-формат — юнит-тест сериализации.

## Порядок реализации (для плана)

1. **Эмпирика:** LHM-дамп сенсоров на целевой матери — убедиться, что +12V читается адекватно
   (иначе пересмотр по rail). Прочие сенсоры проверить заодно.
2. NuGet `LibreHardwareMonitorLib` в `SzDiag.Agent`.
3. `ISensorSource` + `SensorSnapshot` + `LhmSensorSource` (+ живой тест под флагом).
4. `MonitorThresholds` + `PowerMonitor` + `PowerSummary` (юнит-тесты на fake-источнике).
5. `HubRoutes.PowerAlert` + `AgentHub` + отражение в CLI `watch`.
6. Интеграция в `TestRunner.Run` (сквозной режим по флагу конфига).
7. `szcli power run <СЗ> <минуты> [--occt]` (CLI + `/api` + SignalR-команда агенту).
8. `RevertState.MonitorDriverLoaded` + ветка в `Revert`.
9. Секция в `ReportMarkdownBuilder` + CSV-артефакт.
10. `build-dist` — проверить, что LHM-зависимость едет в self-contained пакет агента.

## Открытые вопросы

- Точная эвристика «просадки частот» — калибруется на первом живом прогоне.
- Читается ли +12V на конкретной матери (ASUS для 159873 / Gigabyte B850 для сборок) — пункт 1.
- Гранулярность realtime-алертов (один на сенсор за прогон? повтор после N минут восстановления?)
  — по умолчанию один на сенсор, уточнить при обкатке.

## Находки живой обкатки (2026-07-23, СЗ 159873 + 160176)

Прогнали LHM-логгер (внешняя тулза `lhmmon`, self-contained, CSV 1/с с flush) на двух живых
СЗ параллельно OCCT Power. Результаты корректируют дизайн:

- **Эмпирика п.1 закрыта — rail +12V/5V/3.3V LHM НЕ читает** ни на ASUS (159873), ни на MSI
  B850 GAMING PLUS WIFI6E/MS-7E80 (160176): в Voltage только CPU Core VID. Super I/O не раскрыт. **Вывод: на массовом
  железе сервиса rail-мониторинг через LHM недоступен** — «слабое место» из дизайна подтвердилось
  как обычный случай, а не исключение. Ядро (temps/clocks/GPU power/load) LHM закрывает; для rail
  нужен другой источник или отказ (полагаться на факт воспроизведения + косвенные метрики).
- **Конфликт ring0-драйверов OCCT ↔ LHM (WinRing0):** при параллельной работе OCCT его драйвер
  держит CPU SMU/MSR, и LHM отдаёт **CPU Package power / Tctl = 0.0**. GPU (через NVML, не ring0)
  читается нормально. **Следствие для дизайна: наш `LhmSensorSource` должен быть единственным
  ring0-читателем.** Если power-monitor работает во время внешнего OCCT — CPU-сенсоры будут пустые.
  Либо monitor сам создаёт нагрузку (без OCCT), либо OCCT-режим мониторит только GPU/то, что не
  требует ring0. Отразить в `PowerMonitor`: помечать нечитаемые сенсоры, не выдавать ложный алерт
  на 0.0.
- **Сильнейший аргумент за monitor ВНУТРИ агента (а не внешний процесс/SSH):** под OCCT Power
  входящий SSH к клиенту полностью глохнет (`Connection timed out` — sshd задушен нагрузкой), а
  heartbeat агента лагает за таймаут → hub ложно метит СЗ offline, хотя ОС жива. Внешний logger
  пришлось запускать **detached через scheduled task под SYSTEM** (Start-Process через SSH-сессию
  умирает при её закрытии — портативный sshd убивает дочерние процессы). Встроенный в агента
  monitor этих плясок не требует: агентский SignalR-канал (исходящий WS) переживает нагрузку, и
  realtime-алерт (`PowerAlert`) уйдёт на hub даже когда SSH мёртв.
- **Что LHM реально отдаёт на этом железе (ориентир по покрытию):** GPU Package/Board power, GPU
  Core/HotSpot темпы (MemJunction = 255 заглушка), CPU Total load, частоты по ядрам, CPU Core VID.
  Package power/Tctl — только если LHM единственный ring0-клиент. Rail — нет.
- **Приладовый подпис питания сработал даже без 12V:** «температуры в норме + мгновенный обрыв
  CSV на пике потребления без деградации» = питание (не термотроттлинг). То есть даже неполный
  набор сенсоров (без rail) даёт диагностическую ценность для power-дефектов — стоит заложить в
  отчёт секцию «поведение перед обрывом» (последние N строк CSV), а не только min/max/avg.
- **Доставка тулов на клиент — только SMB с кредами** (ConPTY-stdin через портативный sshd виснет
  на EOF; scp/sftp не подняты; гостевой SMB на Win10/11 закрыт). См. CLAUDE.md / память.
