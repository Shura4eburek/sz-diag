# Журнал СЗ: ничего из процесса диагностики не теряется

Дата: 2026-08-19
Статус: дизайн утверждён, реализация не начата

## Проблема

**СЗ 160697 (2026-08-10).** Всё, что делала система, легло в kb автоматически: `diag run`,
`reboots`, `sensors`, воспроизведённый вырубон под OCCT (20 хв 06 с на EXPO 6000).
Всё, что делали руки у машины — **пропало**:

- мастер снял штатный БП Gigabyte UD850GM и поставил тестовый — в kb ни слова;
- выключался ли при этом EXPO — неизвестно;
- чем кончился прогон на тестовом БП (и был ли он) — неизвестно.

Последняя правка vault по этой СЗ — коммит `5ab98ea` от **10.08 17:38**. Дальше девять дней
тишины: ни записи в `Журнал/`, ни строки в `дії.md`, ни одной сессии в `hub-2026081*.log`.
Заявка всё это время висела открытой, с непустой очередью «Далі» и **замороженным WU**
(`dist/host/cli/freeze/160697.json` на месте), и ни один механизм об этом не заорал.

Итог: результаты дискриминатора (профиль против стока, штатный БП против тестового)
утрачены, тестировать придётся заново.

Два независимых провала:

1. **Ручное физическое действие негде зафиксировать дёшево.** Единственный путь —
   продиктовать в чат, чтобы Claude дописал в `дії.md`. Сессия кончилась → канал закрыт.
2. **Незакрытая заявка молчит.** Машина ушла в offline и исчезла из `list`/`watch`.
   Открытая СЗ с недоделанной очередью ничем не отличается от закрытой.

Усугубляющий фактор: `szcli test run` не фиксирует, **в какой конфигурации** гоняем.
Прогон без метки конфигурации через неделю нечитаем — непонятно, что с чем сравнивать.

## Цель

Контекст диагностики оседает в kb **по ходу процесса**, а не пересказом в конце дня:

- каждое действие (командой или руками) оставляет строку с таймстампом;
- каждый прогон несёт метку конфигурации — прогон без неё невозможен;
- смена железа, видимая софтом (EXPO, частота памяти, GPU, BIOS), фиксируется **сама**;
- открытая заявка с висящим хвостом видна и когда машина offline;
- закрыть заявку с пустым `висновок.md` нельзя без явного `--force <причина>`.

Критерий готовности: воспроизвести сценарий 160697 — после свапа БП и выключения EXPO
в kb остаётся полная картина без единого слова в чате, а незакрытая заявка всплывает
в начале следующей сессии.

## Ключевые наблюдения по текущему коду

- `KbPaths` (`src/SzDiag.Kb/KbPaths.cs`) — единственное место с именами файлов СЗ
  (`запит.md`, `діагностика.md`, `дії.md`, `висновок.md`, `logs/`, `reports/`).
  Новый файл журнала добавляется сюда, больше нигде строк быть не должно.
- В kb автоматически пишет **hub** (скелет по СЗ через `KnowledgeBaseScaffolder`, отчёты,
  бэкап через `KbBackupService`). `дії.md` после скелета не трогает никто — он ведётся руками.
- `SessionRegistry` держит только **активные** сессии в памяти; `GetActive()` отдаёт
  `SessionInfo` (`src/SzDiag.Contracts/SessionInfo.cs`). История и вырубоны — в SQLite через
  `ISessionStore` (`RecordOpenAsync`/`RecordCloseAsync`/`RecordRebootAsync`/`GetRebootsAsync`).
  Значит «открыта, но offline» технически известно, просто нигде не показывается.
- `ManagementApi` (`src/SzDiag.Hub/ManagementApi.cs`) — единая точка, через которую проходят
  **все** команды CLI (`test`, `diag`, `exec`, `push`, `pull`, `close`, `maintenance`).
  Один хук здесь ловит весь поток действий.
- CLI знает `KbRoot` локально (`src/SzDiag.Cli/appsettings.json`), но писать журнал с двух
  сторон — гонка за файл. Писатель должен быть один.
- `szcli close` уже умеет кричать про забытый unfreeze — прецедент гейта есть, идём тем же путём.

## Решение

**Hub — единственный писатель журнала.** CLI отправляет записи через новый endpoint;
hub дописывает и их, и свои собственные события (⚡ смена `bootTime`, offline/online,
неполный откат) в один файл `kb/СЗ/<номер>/журнал.md`.

Почему не «CLI пишет сам»: половина ценного рождается не от команды, а на стороне hub —
вырубон, потеря связи, срабатывание watchdog. Через CLI они в журнал не попадут.

Почему не «событийный лог в SQLite + рендер markdown»: два источника правды и заметно
больше работы ради надёжности, которой markdown-append и так хватает (файл под git,
бэкапится каждые 15 минут). Понадобится — SQLite кладётся сверху позже, формат не мешает.

## Компоненты и изменения

### 1. `KbPaths` — новые пути

```csharp
public string Journal(string sz) => Path.Combine(SzDir(sz), "журнал.md");
public string SnapshotsDir(string sz) => Path.Combine(SzDir(sz), "snapshots");
```

### 2. `SzJournal` (новый, `src/SzDiag.Kb/SzJournal.cs`)

Единственное место, знающее формат журнала.

```csharp
public sealed record JournalEntry(DateTimeOffset At, JournalSource Source, string Text);
public enum JournalSource { Command, Manual, Machine, Snapshot }

public sealed class SzJournal
{
    public void Append(string sz, JournalEntry entry);          // атомарная дозапись
    public DateTimeOffset? LastEntryAt(string sz);              // для stale-детекта
    public IReadOnlyList<JournalEntry> Tail(string sz, int n);  // для `szcli todo` и сводки
}
```

Формат файла — плоский markdown, дозапись только в конец, заголовок дня заводится при
первой записи за дату:

```markdown
# Журнал 160697

## 2026-08-10
- **17:02** `freeze` — WU заморожено
- **17:04** `test run occt` — старт; конфігурація: **EXPO 6000, штатний БЖ**
- **17:21** ⚡ **вирубон** — протрималась 20 хв 06 с під навантаженням
- **17:38** ✋ майстер зняв Gigabyte UD850GM, поставив тестовий Corsair RM850x
- **17:52** 🔧 знімок заліза: RAM Configured **6000 → 4800** (EXPO вимкнено)
```

Контент — украинский, как весь остальной kb. Префиксы: без значка — команда, `✋` — рука
мастера, `⚡` — событие машины, `🔧` — дифф снапшота.

Заголовок дня и запись пишутся одной операцией под файловым локом; при конкурентной записи
(hub-событие в момент команды) второй писатель ждёт. Файл целиком не читается — для
`LastEntryAt` берётся хвост.

`висновок.md` и `дії.md` не меняются: журнал — сырьё, `дії.md` остаётся человеческим
пересказом. Даже если пересказ не сведён — сырьё в vault и под бэкапом.

### 3. `JournalWriter` (новый, `src/SzDiag.Hub/JournalWriter.cs`)

Тонкий сервис поверх `SzJournal`, зарегистрирован в DI hub. Знает, как назвать каждое
действие человеческим языком, и глотает свои ошибки: **падение записи в журнал никогда
не валит саму команду** (пишет в `hub-<дата>.log` и живёт дальше).

Вызовы:

| Откуда | Что пишется |
|---|---|
| `ManagementApi` — `test`, `diag`, `exec`, `push`, `pull`, `close`, `maintenance` | факт команды и исход (принято/ошибка); для `test`/`diag` — старт и финиш отдельными строками |
| заморозка/разморозка WU (`freeze`/`unfreeze`) | состояние WU на клиенте |
| `SessionRegistry.Register` / `MarkOfflineByConnection` / `MarkStaleOffline` | online / offline |
| детект смены `bootTime` (там же, где `RecordRebootAsync`) | ⚡ вырубон: сколько продержалась, чем была занята |
| `RevertCoordinator` при неполном откате | ⚠️ остаток доступа на машине |

### 4. `POST /api/sessions/{sz}/journal` и `szcli note`

```
szcli note 160697 "майстер зняв Gigabyte UD850GM, поставив тестовий Corsair RM850x"
```

DTO `JournalNoteRequest(string Text)` в `SzDiag.Contracts`. Endpoint **не требует активной
сессии**: мастер отходит от машины, агент может быть уже offline, а заметку принять
обязаны. Проверка только на валидность номера (`SzNumber`) и непустой текст; если папки
СЗ в kb ещё нет — заводится скелет (`KnowledgeBaseScaffolder`), как при `kb record`.
Источник записи — `JournalSource.Manual`.

### 5. Метка конфигурации у прогона

`szcli test run <СЗ> [фильтр] --config "<текст>"` — без метки команда **не стартует**.

- Метка едет в `POST /api/sessions/{sz}/test` (новое поле `Config` в теле запроса),
  hub кладёт её в журнал строкой старта и в шапку `report.md`.
- Hub хранит последнюю метку по СЗ в SQLite (`ISessionStore`, новая пара
  `SetLastTestConfigAsync`/`GetLastTestConfigAsync`).
- Повтор без `--config` — отказ с подсказкой: `прошлый прогон: «EXPO 6000, штатний БЖ» —
  повторить ту же конфигурацию: --same-config`. Флаг `--same-config` берёт сохранённую метку.

Это и есть страховка от 160697: сравнение «профиль против стока» невозможно потерять,
потому что каждая половина сравнения подписана в момент запуска.

### 6. Автоснапшот железа и дифф

Перед стартом прогона (`test run`, `diag run`) hub просит агента отдать компактный снимок
конфигурации. Новая секция RunDiag `snapshot` переиспользует уже существующий сбор, но
отдаёт машинно-читаемый JSON, а не markdown:

- модули памяти: производитель, парт-номер, объём, `Speed` (JEDEC) и `ConfiguredClockSpeed`;
- CPU, версия и дата BIOS материнской платы;
- GPU и версия драйвера, мониторы и на каком адаптере висят;
- диски: модель, серийник, прошивка.

Снимок ложится в `kb/СЗ/<номер>/snapshots/<время>.json` — JSON мелкий (единицы КБ), в
отличие от дампов и CSV его держать в git можно. В журнал пишется **только дифф с
предыдущим снимком**, человеческой строкой:

```
- **17:52** 🔧 знімок заліза: RAM Configured **6000 → 4800** (EXPO вимкнено)
- **18:40** 🔧 знімок заліза: без змін
```

БП софтом не виден — его закрывает `szcli note`. Всё, что видно софтом, фиксируется без слов.

### 7. Stale-детект: `szcli todo`, подсветка, гейт в `close`

**Признак «заявка висит»** — открытая СЗ (есть `RecordOpenAsync`, нет `RecordCloseAsync`),
у которой выполняется хотя бы одно:

- последняя запись журнала старше `Hub.StaleSzHours` (по умолчанию 12);
- активна заморозка WU (`dist\host\cli\freeze\<СЗ>.json` на месте);
- `висновок.md` — пустой скелет (маркер: блок «Для клієнта» с многоточиями не заполнен).

Изменения:

- `GET /api/sessions/stale` — список таких СЗ с причиной, последней записью журнала и
  хвостом очереди «Далі» из `дії.md`. Работает **и для offline-машин**: читает SQLite и kb,
  а не только `SessionRegistry`.
- `szcli todo` — печатает этот список одним экраном. Гоняется первым делом в новой сессии:
  лечит ровно тот сценарий, где чат кончился, а заявка забылась.
- `szcli list` / `watch` — такие СЗ висят красной строкой даже когда машина offline
  (сейчас они просто исчезают из таблицы).
- `szcli close` — отказ, если `висновок.md` скелет или в `дії.md` непустая очередь «Далі».
  Обход: `--force "причина"`, причина уходит в журнал строкой. Существующий крик про
  забытый unfreeze остаётся как есть.

## Обработка ошибок

- **Запись в журнал упала** (vault занят, диск, права) — команда всё равно выполняется,
  ошибка в `hub-<дата>.log` с номером СЗ и текстом записи, чтобы восстановить руками.
  Обратное недопустимо: журнал не должен становиться единой точкой отказа диагностики.
- **Конкурентная запись** hub-события и команды — файловый лок в `SzJournal.Append`,
  ожидание с таймаутом 5 с; по таймауту — как «запись упала» (см. выше).
- **Папки СЗ в kb нет** (заметка пришла раньше первого коннекта) — заводится скелет, потом запись.
- **Агент не отдал снапшот** (offline, задавлен нагрузкой) — прогон стартует всё равно,
  в журнал идёт `🔧 знімок заліза: не вдалося зняти (агент не відповів)`. Метка `--config`
  при этом обязательна и никуда не девается — она и есть человеческая страховка.
- **`--force` при `close` без причины** — отказ: пустая причина хуже отсутствия гейта.

## Тестирование (TDD)

Юнит-тесты (`tests/SzDiag.Kb.Tests`, `tests/SzDiag.Hub.Tests`, `tests/SzDiag.Cli.Tests`):

- `SzJournal`: первая запись заводит шапку и заголовок дня; вторая за тот же день не
  задваивает заголовок; запись на следующий день заводит новый заголовок; `LastEntryAt`
  на пустом и на отсутствующем файле; `Tail` короче запрошенного; кириллица и `**` в тексте
  не ломают файл; конкурентная запись из двух потоков не теряет строк.
- `JournalWriter`: исключение внутри `SzJournal` не прорастает наружу — команда выживает.
- `ManagementApi`: `test` без `Config` → 400 с текстом подсказки; `--same-config` при
  отсутствии сохранённой метки → 400; успешный прогон пишет ровно две строки (старт и финиш).
- Snapshot-дифф: EXPO 6000→4800 даёт строку про выключенный EXPO; идентичные снимки дают
  «без змін»; отсутствие предыдущего снимка не падает.
- Stale-детект: открытая СЗ с записью 13 часов назад — в списке; закрытая — нет;
  открытая с активным freeze и свежей записью — в списке (причина «WU заморожено»);
  скелетный `висновок.md` детектится, заполненный — нет.
- `close`: скелетный `висновок.md` → отказ; `--force` без причины → отказ;
  `--force "причина"` → закрытие и строка в журнале.

Живой прогон на следующей заявке: пройти сценарий 160697 целиком (прогон на профиле →
`note` про свап → прогон на стоке) и убедиться, что `журнал.md` читается как история
без единого слова в чате.

## Фазы реализации

1. `KbPaths` + `SzJournal` + `JournalWriter` + endpoint + `szcli note` + подключение к
   командам `ManagementApi` и событиям `SessionRegistry`.
   **Закрывает случай 160697 на 80%.**
2. Метка конфигурации: `--config` / `--same-config`, хранение последней метки, шапка отчёта.
3. Автоснапшот железа и дифф в журнал.
4. `szcli todo`, `GET /api/sessions/stale`, подсветка в `list`/`watch`, гейт в `close`.

## Осознанно вне scope (YAGNI)

- Событийный лог в SQLite с рендером markdown — формат журнала не мешает добавить позже,
  если файл окажется ненадёжным.
- Автосведение `дії.md` из журнала — журнал сырьё, `дії.md` смысл; сведение остаётся
  человеческой работой.
- Уведомления наружу (почта, телега) про зависшие СЗ — `szcli todo` в начале сессии
  и красная строка в `watch` покрывают потребность.
- Фиксация того, что софтом не видно (БП, кулер, термопаста) — только через `szcli note`,
  автоматике взяться неоткуда.
