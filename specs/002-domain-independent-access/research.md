# Research: Доступ без своего домена

Дата: 2026-11-24. Источники и проверки — в конце каждого пункта.

## R1. Хранение секретов флота

- **Decision**: бандл секретов флота шифруется **паролем флота** (AES-256-GCM, ключ из пароля через
  PBKDF2-SHA256, 600 000 итераций, соль 16 байт) и кладётся переменной `SZDIAG_FLEET_BUNDLE`
  сервиса `szdiag-signpost`. Читает его **только `build-dist` через залогиненный `railway` CLI
  оператора** (`railway variables --service szdiag-signpost --json`). HTTP-эндпоинта `/fleet` нет.
- **Rationale**: переменные Railway попадают в env работающего процесса. Если там лежит открытый
  приватный ключ подписи, сервис может подписать любую запись — FR-004 рушится. Шифротекст плюс
  доступ только через аккаунт Railway дают два независимых барьера (аккаунт + пароль), а сервис
  не имеет ни того, ни другого.
- **Alternatives**: `/fleet` по админ-токену (сервис держит секрет в открытую — отвергнуто);
  ручное копирование `secrets\` между машинами (работает, но это и есть сегодняшняя боль);
  менеджер паролей (нет CLI-интеграции у оператора).

## R2. Алгоритм подписи

- **Decision**: **ECDSA P-256 / SHA-256 из BCL .NET 8** (`System.Security.Cryptography.ECDsa`).
  Подписываются **сырые байты** полезной нагрузки; конверт `{ "payload": base64, "sig": base64,
  "kid": "..." }` — без пересериализации JSON перед проверкой.
- **Rationale**: Ed25519 в BCL .NET 8 нет; ECDSA P-256 есть на Windows и Linux (Railway) без
  сторонних пакетов и дружит с single-file. `kid` — отпечаток публичного ключа, задел на ротацию.
- **Alternatives**: Ed25519 через BouncyCastle.Cryptography/NSec (лишняя зависимость в Contracts,
  NSec тянет нативный libsodium); RSA (длинные ключи без выигрыша).

## R3. Апдейтеру ZeroTier не нужен

- **Decision**: апдейтер берёт **подписанный пакет** с hub в LAN, иначе со своего указателя.
  В ZT-сеть входит **только агент**.
- **Rationale**: пакет секретов не содержит (проверено листингом `package.zip`: exe, `ssh\`,
  `service_key.pub`, `testsuite.json`, `version.txt`; `appsettings.json` исключён в `build-dist`).
  Сценарий «на клиент кладём Updater.exe + appsettings» сохраняется; апдейтер не тянет нативную
  `libzt.dll` и не распаковывает её в `%TEMP%` (след). Один член сети на клиента, а не два.
- **Alternatives**: libzt и в апдейтере (два члена сети, нативка в `%TEMP%` при single-file).

## R4. Зеркало — отклонено (решение владельца, 2026-11-24)

- Было: GitHub Release публичного репозитория с подписанными `hub.json`/`release.json` и пакетом.
- **Отклонено**: на GitHub не должно уходить ничего — ни адреса hub, ни исполняемые файлы.
  Каждый собирает проект под себя и держит свой Railway. Указатель недоступен — остаются LAN и
  прежний конфиг клиента; второй указатель при нужде добавляется в `HubLocator.Sources()`.

## R5. Сервис указателя на Railway

- **Decision**: новый проект решения `src/SzDiag.Signpost` (ASP.NET Core minimal API, net8.0,
  Dockerfile, деплой `railway up` вручную) — сервис `szdiag-signpost` в своём проекте Railway
  оператора; адрес (`https://<сервис>.up.railway.app`) в репозиторий не пишется.
  Состояние: последний конверт hub (в памяти) и релиз + пакет (на volume `/data`).
  Сервис **проверяет подпись** на каждом `PUT` публичным ключом из env (`SZDIAG_SIGN_PUBKEY`) —
  отдельный токен записи не нужен: подписать может только hub с приватным ключом.
- **Rationale**: тот же стек, что hub; аренда в памяти теряется при редеплое, но hub-ы
  переопубликуют её за 30 с. Соседние сервисы проекта не трогаем. Деплой без GitHub-триггеров.
- **Стоимость**: укладывается во включённые в Hobby $5/мес (~235 ₴) кредиты; трафик — десятки МБ
  на заявку.

## R6. Свежесть и replay

- **Decision**: в каждом конверте — `seq` (unix-мс издателя, монотонный) и `issuedAt`.
  Сервис указателя отвергает `PUT` с `seq` ≤ текущего для того же типа записи (кроме `takeover`).
  Клиент хранит последний принятый `seq` рядом с exe (`signpost-seen.json`) и не принимает
  меньший; пакет не ставится, если `buildTime` релиза старше установленного (`build-info.json`
  в пакете). Часы клиента не используются.
- **Rationale**: закрывает replay старой честно подписанной записи и edge case со сбитыми часами.
- **Ограничение**: seq клиента хранится по виду записи, а не по `hubId`. Если hub переезжает
  ПК → ноут, а часы ноута отстают сильнее интервала публикации, клиенты примут его запись за
  replay. Машинам hub нужна синхронизация времени (NTP Windows по умолчанию включён) — проверка
  в `doctor.ps1` (T053).

## R7. Аренда hub

- **Decision**: hub публикует конверт `hub` при старте и каждые 30 с; аренда = `issuedAt` + 90 с
  по часам **сервиса**. `PUT` от другого `hubId` при живой аренде → `409` с данными держателя;
  с `takeover: true` в подписанной нагрузке — принимается. Hub, потерявший аренду, видит `409`
  со своим `hubId` не держателем и пишет в лог/`/api/status`.

## R8. libzt в агенте (гейт — спайк, фаза 3 плана)

Проверено:
- NuGet `ZeroTier.Sockets` — стабильная **1.8.4** (есть `lib/net5.0`, `runtimes/win10-x64/native/libzt.dll`).
- `libzt.dll` — PE machine **0x8664** (x64). Репо `zerotier/libzt` не архивировано, последний пуш 2026-07-30.
- Лицензия — BSL 1.1, Change Date 2026-01-01 → Apache 2.0 (см. результаты спайка ниже).

Не проверено — **спайк обязан подтвердить до фазы 4**:
1. Пакет грузится под net8.0 win-x64; нативка лежит **рядом с exe** (не self-extract в `%TEMP%`).
2. HttpClient поверх ZT: `SocketsHttpHandler.ConnectCallback` → `Stream`-обёртка над zts-сокетом.
3. SignalR поверх ZT: `HttpConnectionOptions.HttpMessageHandlerFactory` + `WebSocketFactory`
   (`ClientWebSocket.ConnectAsync(uri, HttpMessageInvoker, ct)`); фоллбэк — ServerSentEvents.
4. Входящий accept на ZT:22 → прокси на `127.0.0.1:<sshPort>`; пропускная способность ≥ quick tunnel.
5. Куда libzt пишет identity/peers (`zts_init_from_storage(path)` → `C:\ProgramData\szdiag\zt\<СЗ>`)
   и что именно стирать в Revert; случайный порт (`zts_init_set_port(0)` или эквивалент).
6. Время до `ONLINE` + получения адреса в типовой сети (SC-006: ≤ 60 с).

Провал пункта 1–3 → ZT-часть уходит в отдельную спеку, фазы 1–2 поставляются без неё.

Обе ноды гонялись на одном боксе в сети пробного контроллера на Railway: функционально это
полный путь, но скорость **не репрезентативна** (путь мог быть локальным), реальную меряем на
живой заявке против quick tunnel (~17 МБ/с).

**⚠ Баги `ZeroTier.Sockets` 1.8.4 — их `Send`/`Receive` и `NetworkStream` не использовать:**
- `Send(buf, offset, size)` передаёт в `zts_bsd_send` длину **всего массива** (`Buffer.ByteLength`),
  а не `size` → в поток уходит мусорный хвост буфера;
- `Receive(buf, offset, size)` так же: при `offset > 0` нативный `recv` пишет **за границу** массива;
- оба берут адрес массива через `Marshal.UnsafeAddrOfPinnedArrayElement` **без закрепления**, а
  вызов блокирующий — GC может сдвинуть массив посреди `recv` (порча памяти);
- базовый `Stream.ReadAsync/WriteAsync` (их `NetworkStream` асинхронные не переопределяет)
  сериализует чтение и запись одним семафором — для full-duplex WebSocket это зависание.

Обход (спайк удалён в T054, итог — `src/SzDiag.Agent/Zt/ZtStream.cs` + `LibztSocketIo.cs`, T042): свой
P/Invoke `CSharp_zts_bsd_send/recv` из `libzt` с `fixed`-закреплением и точной длиной; дескриптор
берётся из приватного `_fd` их `Socket` через reflection (Connect/Bind/Listen/Accept у них корректны);
чтение — `LongRunning`-задачей, запись — отдельно, независимо. Тест на это — обязателен в T042.

**Гейт T036: пройден** — пункты 1–3 (и 4–6) подтверждены, US3 продолжается.

Мелочь: после `Stop()` libzt печатает `Socket error: recv, 10093` (WSANOTINITIALISED) — шум
остановки, на результат не влияет; в агенте глушить/не показывать оператору.

**Лицензия снята:** у пакета 1.8.4 BSL 1.1 с `Change Date: 2026-01-01` и `Change License:
Apache 2.0` — на дату спайка эта версия уже под Apache 2.0, ограничение «коммерческий
не-OSI продукт» к ней не применяется. Тариф ZeroTier Central
неактуален: контроллер свой (ниже); открыта только лицензия самого `zerotier-one`.

### Свой контроллер на Railway (проба 2026-11-24)

Схема варианта — `infra-self-controller.html`. Проба: образ `zerotier/zerotier:latest`
(zerotier-one **1.14.2**, Debian 12), без volume, без публичного порта, отдельный сервис в
проекте Railway владельца.

- **Исходящий UDP с Railway работает:** ONLINE за ~6 с, к четырём корням (PLANET) путь
  **DIRECT**, без relay. Входящий порт не нужен.
- **Контроллер встроен в образ:** `GET /controller` → `"controller": true, "databaseReady": true`;
  сеть создаётся `POST /controller/network/<nodeId>______` (пул, маршрут, `v4AssignMode.zt`).
- **Сквозь:** libzt-клиент спайка с бокса вошёл в публичную сеть этого контроллера и получил
  `10.88.0.95` из пула через 5,8 с после join, без ручного authorize.
- Предупреждение `failed to drop privileges … running as root` — особенность контейнера, на
  работу не влияет. TUN в контейнере не нужен: контроллер не входит в сети сам.
- Для боевого сервиса нужен **volume** под `/var/lib/zerotier-one` (identity контроллера =
  префикс ID сети) и HTTPS-прокси к API с токеном hub — в пробе их не было.

Итог: вариант «свой контроллер на Railway» жизнеспособен, VPS не нужен. Открыто: пункты 2–4
спайка (HttpClient/SignalR/проброс SSH) — теперь проверяются на этом же контроллере.

## R9. Сервисная ZT-сеть и посторонние

- **Decision**: свой контроллер на Railway (R8, «Свой контроллер на Railway»; Central отклонён ради независимости инфраструктуры), сеть **публичная** (без ручной авторизации) + flow rules:
  разрешён только трафик к/от ZT-адреса hub, `drop` всего остального (клиент↔клиент запрещён).
  Подсеть `10.88.0.0/24`, hub — статический `10.88.0.1` (назначается API контроллера).
- **Rationale**: ID сети лежит в публичном указателе; приватная сеть требует авторизации до
  первого байта трафика, а авторизовать неизвестного клиента нечем (курица и яйцо). Защиту
  держат токен агента + секрет сессии, как сейчас.
- **Последствия**:
  - Management API режется по `HttpContext.Connection.LocalIpAddress`: запрос пришёл на адрес из
    сервисной подсети → `403` (не bind на конкретные IP — у ноута LAN по DHCP).
  - То же для личной ZT-сети: `Hub.DenySubnets` (по умолчанию `10.199.89.0/24`) — hub не отвечает
    на запросы, пришедшие на адреса этих подсетей.
  - `ZtMemberSweeper` на hub: члены сети без активной СЗ старше 10 мин удаляются через API
    (посторонние не забивают лимит; добирает то, что headless-откат не удалил).
  - Удаление члена при закрытии СЗ делает hub (у клиента нет токена контроллера — FR-023).
  - Revert headless (`--revert`): агент поднимает ZT **одноразовым** storage (`zt\revert-*`: при живом
    агенте его нода с identity СЗ ещё в сети — две ноды с одной identity мешали бы друг другу),
    шлёт статус отката, затем стирает оба storage (свой и СЗ из состояния). Не поднялся ZT → статус не уходит (как сейчас при недоступном hub),
    член сети добирает сторож.
- **Боевая сеть заведена (T037, 2026-11-24)** `tools/zt-network.ps1` на своём контроллере: 14 правил
  (ARP+IPv4; к/от `10.88.0.1`/`.2` — accept; остальное — drop). Проверено: hub(бокс, ZeroTier
  One) → libzt-клиент — `pong`; libzt-клиент → libzt-клиент — соединение не устанавливается.
  Адаптер сети на боксе — профиль Windows **Public**.
- **Порты hub правила не режут:** stateless-правилам нечем отличить ответ ssh клиента от нового
  соединения на любой порт hub (sport подделывается). Входящее на hub-машину держит Windows
  Firewall: на боксе hub разрешён для Public (`szdiag.hub.exe`, любой порт, и `szdiag-hub-5099`),
  прочее Public по умолчанию закрыто. Hub слушает `0.0.0.0:5099` — **до T048 (LocalAddressFilter)
  `/api` с ZT-адреса закрыт только management-токеном**; поэтому `ztNetwork` в указатель
  (T049) публикуется только после T048.
