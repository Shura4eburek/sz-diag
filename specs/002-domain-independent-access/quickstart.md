# Quickstart: проверка фичи

Предусловия: `railway` залогинен, свой проект Railway слинкован; две машины-hub
(ПК, ноут); клиентская машина/ВМ вне LAN hub; пароль флота у оператора.

## Фаза 1 — ключи флота (US2)

1. ПК: `.\tools\fleet.ps1 init` → в Railway появилась `SZDIAG_FLEET_BUNDLE` (шифротекст);
   повторный `init` → код 2.
2. Ноут: удалить `secrets\`, `.\tools\build-dist.ps1` → спрашивает пароль, раскладывает `secrets\`;
   неверный пароль → код 4, сборка не идёт, новые ключи **не** генерируются.
3. Апдейтер из dist ноута → hub ПК: агент регистрируется. И наоборот (SC-003).
4. Старый апдейтер (до фичи) → hub на ключах флота: принят по `ExtraAgentTokens`.

## Фаза 2 — указатель (US1, US4)

1. `railway up --service szdiag-signpost` (из `src/SzDiag.Signpost`), `GET /healthz` → `ok`.
2. Hub на ПК стартовал → `GET /signpost` показывает `hub` с адресами ПК; `/api/status` — «опубликован, аренда моя».
3. Hub на ноуте без `--takeover` → в консоли «активен hub ПК до …», указатель не изменился.
   Погасить ПК, подождать ≤ 90 с → ноут занял аренду сам (SC-002 ≤ 1 мин после старта).
4. `build-dist -SignpostUrl <свой указатель> -Publish` → релиз на signpost (на GitHub ничего не уходит).
5. Клиент вне LAN, `HubUrl` пуст: апдейтер ставит пакет с signpost; в логе — `LAN: таймаут`, `signpost: ok`.
6. Подмена: подсунуть конверт с испорченной `sig` (локальный прокси) →
   «отвергнут: подпись», переход к следующему источнику (SC-004). Старый конверт (`seq` меньше) → «отвергнут: seq».
7. Signpost остановлен → апдейтер остаётся на LAN/прежнем конфиге, в логе — `signpost: таймаут`.

## Фаза 3 — спайк libzt

Консольный прототип в `spikes/zt-spike/` (не в решении): пункты 1–6 из research R8; результат —
таблица «проверено/провал» в `research.md`. Провал 1–3 → фаза 4 отменяется.

## Фаза 4 — ZT-доступ (US3)

1. Hub-машина в сервисной сети, статический `10.88.0.1`; личная сеть `10.199.89.0/24` по-прежнему работает.
2. Клиент: агент открыл доступ → `szcli target <СЗ>` → `mode: zt`, ssh-строка работает (SC-006 ≤ 60 с).
3. Второй клиент: `Test-NetConnection <zt-ip первого> -Port 22` → провал (flow rules).
4. С устройства из личной ZT-сети: запрос на `http://10.199.89.217:5099/api/sessions` → отказ.
5. `szcli close <СЗ>` → в контроллере члена нет (`GET /controller/network/{nid}/member` через прокси); на клиенте нет `C:\ProgramData\szdiag\zt\`, задач и процессов (SC-005).
6. Убить агента без отката → через 10 мин сторож удалил члена сети.
7. Сломать ZT (блок UDP) → агент упал на quick tunnel, `target` показывает причину.

Автотесты: `dotnet test` — подпись/конверт, seq/replay, аренда, резолвер с фейковыми источниками,
`RevertState`-пара для ZT-шага, фильтр `DenySubnets`/management.
